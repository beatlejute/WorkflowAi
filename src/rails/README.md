# Rails — ядро принуждения процедур скилов

Реализация концепции «Рельсы для агента» для workflow-ai: процедура скила записана
графом (mermaid в `SKILL.md` + фрагменты в `workflows/*.md`), соблюдение графа
принуждается детерминированными хуками, которые отклоняют вызов инструмента.
Хуки обязаны одинаково работать для двух исполнителей: **Claude Code** (`claude -p`,
интерактивная сессия) и **Kilo** (`kilo run --auto`). Один модуль ядра, два тонких адаптера.

Этот документ — спецификация для реализации. Всё, что здесь не описано, решается
по принципу «детерминированно, дёшево, без вызова модели».

## 1. Состав

```
src/rails/
  README.md          — этот документ
  graph.mjs          — парсер mermaid-подмножества, модель графа, валидация
  rails-config.mjs   — загрузка и валидация rails.yaml скила
  state.mjs          — состояние сессии (файл), переходы, счётчики, потолки
  journal.mjs        — журнал отказов (jsonl), счётчики повторов по узлу, отчёт
  actions.mjs        — нормализация действий (инструмент Claude / Kilo → action)
  core.mjs           — decide(): единая логика решений
  write-policy.mjs   — физическая классификация целей записи: канон, protected, независимая копия (§15)
  runtime-snapshot.mjs — закреплённый рантайм запуска: снимок config+graph, полномочия текущей сессии (§15)
  output-check.mjs   — проверка финального ответа агента по rails.yaml.output
  claude-hook.mjs    — адаптер Claude Code hooks (stdin JSON → stdout JSON)
  kilo-plugin.mjs    — адаптер Kilo/opencode plugin (tool.execute.before / after)
  cli.mjs            — rails start | goto | status | reset | report | check | coverage | selfcheck
src/scripts/check-rails-graph.js     — обёртка над `cli check` (привычный путь для агентов)
src/scripts/check-rails-coverage.js  — обёртка над `cli coverage`
src/tests/rails-*.test.mjs           — тесты (node:test, как остальные в src/tests)
```

Зависимости: только Node ≥ 18 и `src/lib/js-yaml.mjs` (уже в репозитории). Никаких новых npm-пакетов.
Все модули — ESM, без побочных эффектов при импорте (адаптеры и CLI запускают логику только
из `main()`), чтобы тесты импортировали их напрямую.

## 2. Пути и разрешение путей

| Что | Где |
|---|---|
| Корень проекта | `findProjectRoot(cwd)` из `src/lib/find-root.mjs` (ищет `.workflow/`). Нет корня → хук молчит. |
| Скил | `<root>/.workflow/src/skills/<skill>/` — `SKILL.md`, `workflows/*.md`, `rails.yaml` |
| Ядро rails в проекте | `<root>/.workflow/src/rails/` — junction на `~/.workflow/rails/` (см. §11) |
| Состояние | `<root>/.workflow/state/rails/<sessionId>.json` |
| Память «сессия → корень» | `<WORKFLOW_HOME\|~/.workflow>/state/rails-sessions.json` — для сессий из каталога-зонтика: заполняется `rails start --session` из каталога проекта и edit/write с путём внутри проекта; хук берёт из неё корень для команд без пути (`session-memo.mjs`). ≤ 50 записей: при переполнении первыми уходят записи с исчезнувшим корнем (временные проекты тестов/раннера), потом самые старые. Тесты изолируют её через `WORKFLOW_HOME` (`src/tests/_rails-home.mjs`, преднагрузка `npm test`) |
| Журнал отказов | `<root>/.workflow/logs/rails-denials.jsonl` (только дописывание) |

**Сравнение путей — только через realpath.** Скилы подключены junction-цепочкой
(`<root>/.workflow/src/skills/<skill>` → `~/.workflow/skills/<skill>` → канон), и агент может
править файл как по проектному пути, так и по каноническому. Путь считается внутри области,
если `realpath(путь)` начинается с `realpath(область)`. Для ещё не существующего файла (Write)
realpath берётся от ближайшего существующего предка плюс остаток. Регистр букв на Windows
не учитывается.

## 3. Грамматика графа

Граф скила = все блоки ```` ```mermaid ```` из `SKILL.md` и из файлов, перечисленных в
`rails.yaml.fragments` (по умолчанию `workflows/*.md`), склеенные в один граф.
Поддерживается подмножество mermaid flowchart:

```
graph TD
    %% комментарий
    P4E1["П4 ВХОД: Правка файлов скила — ..."]
    P4R1["П4 ПРАВИЛО: ..."]
    P4G1{"П4 ГЕЙТ: ...?"}
    P4E1 --> P4R1
    P4R1 --> P4S1["П4 ШАГ: ..."]
    P4G1 -->|"да"| P5E1
    P4G1 -->|"нет"| P4S1
```

- Идентификатор узла: `^P(\d+)([ERSGQ])(\d+)$` — этап, тип, номер. Разбирается регулярным
  выражением, без модели.
- Форма: `["..."]` прямоугольник (E, R, S), `{"..."}` ромб (G, Q). Лейбл только в двойных
  кавычках; может занимать несколько строк (перенос строки внутри кавычек допустим).
- Рёбра: `A --> B`, `A -->|"метка"| B`, определение узла inline в ребре допустимо.
- Типы: `E` вход в этап, `R` правило, `S` шаг, `G` гейт-самоопрос (ответ «нет» — ребро назад),
  `Q` выбор ветки по существу задачи.

Правила валидации (`graph.validate()` возвращает `{errors[], warnings[], stats}`):

| Код | Условие | Уровень |
|---|---|---|
| `bad-id` | идентификатор не по грамматике | error |
| `dup-id` | повтор идентификатора (в том числе между файлами) | error |
| `semicolon-in-label` | `;` внутри лейбла — в кавычках mermaid 12.0.0 разбирает штатно (проверено 2026-09-22), ломает только `;` вне кавычек; наша грамматика требует кавычки | warning |
| `short-label` | лейбл R/S/G/Q короче `quote_min` (по умолчанию 25) символов | error |
| `unknown-target` | ребро на несуществующий узел | error |
| `no-entry` / `bad-entry` | `rails.yaml.entry` отсутствует или не E-узел | error |
| `orphan` | узел недостижим из entry | error |
| `dead-end` | у узла нет исходящих рёбер и он не в `terminal` и не в `pause_nodes` | error |
| `stage-no-entry` | в этапе нет E-узла или их больше одного | error |
| `stage-order` | внутри этапа R-узел определён после S/G/Q | error |
| `gate-edges` | у G/Q меньше двух исходящих рёбер или рёбра без метки | error |
| `stage-collision` | один номер этапа в двух файлах | error |
| `unlabeled-branch` | у узла с двумя и более исходящими рёбрами есть ребро без метки | warning |

Статистика: узлы по типам, рёбра, этапы, файлы. Нормализация лейбла для сверки цитат:
схлопнуть пробелы, привести кавычки `«»“”"` к `"`, `’‘'` к `'`, нижний регистр, убрать
`<br/>`, markdown-акценты `` ` `` и `*`, пиктограммы (`\p{Extended_Pictographic}` — ⛔ ⚠️ ✅ 🟢 …,
кроме `©`), вариационный селектор U+FE0F и ZWJ U+200D: агент при цитировании их опускает
(прогоны analyze-report 2026-09-22 — отказы на узлах с ⛔). Обе стороны сверки — лейбл и
цитата, фраза baseline и текст скила в покрытии — идут через одну функцию. Настоящий разбор парсером mermaid не подключается (нет зависимости); это
осознанная граница, указана в отчёте `check`.

## 4. rails.yaml

Лежит рядом с `SKILL.md`. Машинный конфиг хука, не проза. Схема v1:

```yaml
version: 1
skill: coach
entry: P0E1                      # E-узел
terminal: [P8S3]                 # где разрешён финальный ответ
pause_nodes: [P3Q1, P7S2]        # узлы «вопрос стейкхолдеру»: финальный ответ тоже разрешён
fragments: ["workflows/*.md"]    # где искать фрагменты графа, помимо SKILL.md
quote_min: 25
canary: "echo RAILS_CANARY"      # безвредная команда, которую хук обязан отклонить

write_scope:                     # H1: запись разрешена только сюда (project-relative или abs)
  - ".workflow/src/skills/**"
  - ".workflow/coach-backlog.yaml"
allow_temp: true                 # плюс os.tmpdir() и его поддиректории
write_deny:                      # H1b: запрещено даже внутри scope
  - ".workflow/src/skills/coach/rails.yaml"
  - ".workflow/src/rails/**"

deny_shell:                      # H2: регулярные выражения по тексту команды
  - pattern: "\\bgit\\s+(commit|add|push|checkout|switch|restore|reset|rebase|merge|stash|tag)\\b"
    reason: "Коуч не выполняет git-операции — коммит делает исключительно пользователь"
    incident: "SKILL.md ⛔ «Коуч не выполняет git-операции»"
deny_mcp:                        # имена MCP-инструментов без префикса сервера
  - git_commit
  - git_create_branch
  - git_open_pr

stage_actions:                   # H3: действие разрешено только на перечисленных этапах
  edit_skill:
    kind: [edit, write]
    match: ".workflow/src/skills/**"
    stages: [4, 12, 41]
  run_tests:
    kind: [shell]
    match: "run-skill-tests\\.js"
    stages: [5]
    max_per_session: 3           # H4: потолок на число выполнений
  next_test_id:
    kind: [shell]
    match: "get-next-test-id\\.js"
    stages: [5]
  edit_backlog:
    kind: [edit, write]
    match: ".workflow/coach-backlog.yaml"
    stages: [6]

cycles:                          # H4: потолок на возвраты между этапами
  - from: 5
    to: 4
    max: 3
    reason: "Три круга «правка → тест» не сошлись — выход к человеку"

edge_guards:                     # страж ребра: переход закрыт, пока в проекте есть файл
  - from: P0Q1                   # ответ на выборе/гейте агент даёт сам — где его опровергает
    to: P7E1                     # файл проекта, ребро закрывается фактом
    deny_if_exists: ".workflow/tickets/in-progress/{ticket}.md"   # {ticket} — тикет запуска
    reason: "Тикет запуска в in-progress/ есть — ветка «тикет не найден» закрыта"
    incident: "2026-09-27: «тикет не найден» при тикете в in-progress/, выход со status blocked"

output:                          # H5: выходной слой
  final_requires:                # регулярные выражения (флаг i), все обязаны совпасть — в terminal
    - "RAILS:\\s*P\\d+[ERSGQ]\\d+"
    - "verdict\\s*="
    - "Файлы:"
  pause_requires:                # то же для pause_nodes (вопрос стейкхолдеру, не отчёт); по умолчанию пусто
    - "RAILS:\\s*P\\d+[ERSGQ]\\d+"
  final_forbids:                 # регулярки, которые совпасть НЕ должны — в terminal
    - "(?:^|\\n)[ \\t]*[-*] .+(?:\\n[ \\t]*[-*] .+)+"   # список из 2+ пунктов
  pause_forbids:                 # то же для pause_nodes; по умолчанию пусто
  max_stop_blocks: 2             # сколько раз Stop-хук может вернуть агента на доработку с одного узла (§8)
```

`match` — glob по realpath (для `kind: edit|write`) или регулярное выражение по тексту
команды (для `kind: shell`). Valid-проверка `rails.yaml` — часть `cli check`.

`edge_guards[].deny_if_exists` — путь от корня проекта; `*` допустим только в последнем
сегменте, `**` и `..` — нет: проверка перечисляет один каталог (на Windows имя сравнивается
без учёта регистра). Как в shell-glob, `*` не ловит точечные файлы (`.gitkeep.md` в каталоге
тикетов), если сегмент маски сам не начинается с точки. Считаются только обычные файлы
(симлинк — по цели): каталог с именем по маске ребро не закрывает. `reason` обязателен — его
получает агент в отказе вместе с найденным путём. Страж на ребро, которого нет в графе, —
ошибка `unknown-guard-edge` в `cli check`.

Подстановка `{ticket}` внутри сегментов пути — id тикета запуска (`WORKFLOW_RAILS_TICKET`
ставят раннер стадии и раннер тестов скилов, §11; откуда его берут `goto` и хук — §5,
поле `ticket` состояния): страж смотрит на файл тикета ЭТОГО запуска, а не на любой. Маска
`in-progress/*.md` закрывает ребро из-за любого тикета в `in-progress/`, в том числе чужого
(ревью стража 2026-09-27). Подставляется только id вида `[A-Za-z0-9][A-Za-z0-9_.-]*` (без
разделителей, `..` и масок); тикета нет или он другого вида — страж с `{ticket}`
пропускается и ребро открыто: вне запуска раннера рельсы тикет не знают (fail-open). Другие
подстановки `{…}` — ошибка `bad-glob` в `cli check`.

## 5. Состояние сессии

Файл `<root>/.workflow/state/rails/<sessionId>.json`:

```json
{
  "version": 1,
  "session": "44e7746f-…",
  "run": "wf-run-id или null",
  "ticket": "IMPL-001 или null",
  "skill": "coach",
  "node": "P4S2",
  "started": "2026-09-21T18:00:00.000Z",
  "updated": "2026-09-21T18:05:00.000Z",
  "history": [{ "t": "…", "from": "P4S1", "to": "P4S2" }],
  "counters": { "action:run_tests": 1, "cycle:5>4": 0, "stop_blocks:P4S2": 0 },
  "denials": { "P4S2": 2 },
  "flags": { "correction_pending": false }
}
```

- Идентификатор сессии: Claude — `session_id` из входа хука; Kilo — `input.sessionID`;
  CLI — `--session`, иначе `WORKFLOW_RAILS_SESSION`, иначе единственный файл состояния
  проекта (с предупреждением в stderr). Файлов состояния два и больше, а сессия не задана —
  `status`, `goto` и `reset` отказывают и печатают перечень сессий (инцидент 2026-09-23: в
  проекте работали две сессии коуча, `goto` без `--session` ушёл в самую свежую — чужую — и
  записал в её журнал отказ по чужому узлу).
- Снимок, не событийный лог. Запись атомарная (tmp + rename).
- `start <skill>` создаёт состояние в `entry`. Если состояние уже есть для другого скила —
  отказ, если не `--force`. Если состояния нет, но задан `WORKFLOW_RAILS_SKILL` (ставит раннер),
  хук создаёт состояние сам при первом действии.
- Скил запуска: задан `WORKFLOW_RAILS_SKILL` и у этого скила есть `rails.yaml` — `start` другого
  скила отклоняется (код 2) и с `--force`: по скилу запуска раннер проверяет финальный ответ,
  чужой граф кончается не в его терминале. Отказ называет скил запуска и узел, где сессия
  числится, с переходами оттуда, а без состояния — команду `start <скил запуска>`; пишется в
  журнал (`denial`, `command: "start <skill>"`). Прогон PulseProxy 2026-09-27: claude-haiku на
  стадии execute-task принял «Твоя роль: manual-testing» за скил, получил «используй --force»,
  прошёл граф manual-testing, и раннер отклонил ответ. Второй признак скила запуска — состояние
  сессии с `run` (привязано к запуску раннера): `start` другого скила отклоняется и с `--force`,
  даже если переменной нет или она другая. Префикс `WORKFLOW_RAILS_SKILL=<скил> node …cli.mjs
  start …` (§7, короткое замыкание cli-вызова) подменяет окружение процесса CLI, но хук вставляет
  `--session` своей сессии, а её состояние с `run` и скилом запуска он создал при первом действии —
  раньше, чем выполнится `start`. Не ловится только старт в другой сессии (явный чужой
  `--session` или команда мимо короткого замыкания, без вставки `--session`) с подменённой
  переменной. Имя переменной агенту не называется — ни в отказе, ни в подсказке SessionStart.
- Тикет запуска (`ticket`, для `{ticket}` в `edge_guards`, §4). Хук пишет его в состояние из
  `WORKFLOW_RAILS_TICKET` окружения хоста, когда создаёт состояние при первом действии, —
  раньше, чем выполнится `start`. `start` тикет существующего состояния сессии сохраняет, а без
  состояния берёт `WORKFLOW_RAILS_TICKET` окружения CLI. `goto` и перечни переходов CLI берут
  тикет из состояния, окружение CLI — только если в состоянии тикета нет; перечень в отказе
  хука — тоже из состояния, без него — из окружения хоста. Ревью стража 2026-09-27: `goto` брал
  тикет из окружения CLI, а его команда агента меняет — `WORKFLOW_RAILS_TICKET=… node …cli.mjs
  goto`, пустое значение, `export`/`env`/`unset` перед вызовом. Такую команду хук не считает
  cli-вызовом (§7), но и не отклоняет, если её пропускают общие правила узла (на P0Q1
  execute-task — пропускают), а пустой или чужой тикет открывает страж. Не ловится только
  состояние, которое создал сам `start` с подменённой переменной, а не хук: сессия без хука,
  чужая сессия (явный `--session`) или `reset` и `start` своей сессии одной командой мимо
  короткого замыкания.
- `reset` удаляет файл; факт сброса пишется в журнал.

**Переход `goto <node> --quote "<текст>"`** допустим, если: есть ребро из текущего узла в
целевой; цитата не короче `quote_min`; нормализованная цитата — подстрока нормализованного
лейбла целевого узла. Ошибочная цитата, переход без ребра, пересказ своими словами —
отказ с перечнем допустимых переходов (`id: лейбл → команда`, §7 п.5). Лейбл строки — готовая
цитата из команды, если она — начало лейбла; иначе начало лейбла до 60 символов, обрезанное по
слову и помеченное «…» (`state.allowedTransitions`). Инцидент 2026-09-30 (журнал отказов
execute-task PulseProxy с 29.09: 65 отказов по цитате из 435): `slice(0, 60)` резал посреди слова
(«…а не типо»), и слабая модель дописывала оборванное слово своими словами. Отказ по цитате
называет точку расхождения: совпавший хвост и по ~30 символов дальше у цитаты и у лейбла;
если в лейбле на этом месте `$`, добавляется подсказка про одинарные кавычки (shell
раскрывает `$X` внутри двойных). Так по журналу видно, пересказ это или порча цитаты shell'ом.

**Страж ребра:** если для ребра задан `edge_guards` и файл по `deny_if_exists` в проекте есть,
переход отклоняется (`code: "edge_guard"`) с текстом `reason` и найденным путём. Ответ на
выборе или гейте агент даёт сам; страж закрывает ответ, который опровергает файл проекта
(инцидент 2026-09-27: исполнитель ответил «тикет не найден» при тикете в `in-progress/` и
ушёл к выводу со `status: blocked`, минуя выполнение). Проверяется после цитаты, до потолка
цикла; переход без корня проекта (вызов `applyGoto` без `root`) стражей не проверяет.
Ребро, которое страж закрывает сейчас, в перечнях переходов (`start`, `goto`, `status`, отказ
`start` чужого скила, отказ хука, вердикт повтора раннера) — строкой `id: лейбл — закрыто:
<reason> (есть <путь>)` без команды перехода: слабые модели копируют готовую команду не читая (ревью
стража 2026-09-27). Остальные рёбра — с командой, как обычно. Тикет для `{ticket}` у CLI и
хука — из поля `ticket` состояния (см. выше, «Тикет запуска»), у вердикта повтора — тикет
запуска раннера (§11).

**E-узлы прозрачны:** объявить `goto P4E1` можно, но пока текущий узел — E, действия этапа
(`stage_actions`) запрещены: агент обязан пройти в R/S/G/Q. Так реализовано правило
«цитата из узла-входа не принимается, пока в этапе есть правила, шаги или гейты».

**Потолки:** переход, увеличивающий счётчик `cycle:from>to` сверх `max`, отклоняется с
текстом `reason` и указанием «выход к человеку». Запись `cycles` с `from == to` — потолок
на **возврат внутри этапа** (гейт → шаг): считается только переход в узел, через который
проходит любой путь от входа этапа (`P<n>E1`) к текущему узлу; для узла, недостижимого от
входа, — переход, замыкающий петлю внутри этапа. Штатные шаги вперёд, включая переход гейта
«да» к следующему шагу, счётчик не трогают (первый прогон коуча 2026-09-22 упёрся в
`cycle_limit` на третьем шаге вперёд; прежнее правило «раньше по порядку типов
`E < R < S < G/Q`» считало возвратом каждый переход гейт → шаг, и 2026-09-24 этап разбиения
скила декомпозиции отклонял запись тикетов на четвёртом таком переходе). Действие с
`max_per_session` сверх лимита отклоняется так же.

## 6. Нормализация действий

`actions.mjs` приводит вызов инструмента к `{ tool, kind, command?, path?, server?, mcpTool? }`,
`kind ∈ shell | edit | write | read | agent | mcp | other`.

| Claude Code (`tool_name`) | Kilo (`input.tool`) | kind | поле |
|---|---|---|---|
| `Bash` | `bash` | shell | `command`, `shell: 'posix'` |
| `PowerShell` | — | shell | `command`, `shell: 'powershell'` |
| `Edit`, `MultiEdit`, `NotebookEdit` | `edit`, `patch`, `multiedit` | edit | `file_path` / `notebook_path` / `filePath` |
| `Write` | `write` | write | `file_path` / `filePath` |
| `Read`, `Glob`, `Grep`, `LS` | `read`, `glob`, `grep`, `list` | read | — |
| `Agent`, `Task` | `task` | agent | — |
| `mcp__<server>__<tool>` | `<server>_<tool>` | mcp | server, mcpTool |
| прочее | прочее | other | — |

Неизвестные имена — `other`, никогда не ошибка.

**Запись из shell — `writesTo[]` (ЗАДАЧА C2, 2026-09-22).** Для `shell` ядро вычисляет
`writesTo[] = detectShellWrites(command, { cwd, env, dialect })`. Строку команды разбирает
только `shell-scan.mjs`: сегменты, простые команды, слова с типом кавычек, редиректы и тела
heredoc даёт `scanCommand`, своих трекеров кавычек `actions.mjs` не держит. Правило: всё, что
нельзя вычислить однозначно, даёт маркер `"?"`, и ядро трактует его как запись вне области с
подсказкой «используй Edit/Write или укажи путь явно». Ложный отказ допустим, ложное
разрешение — нет.

**Подсказки отказа — `explainShellWrites`.** Ядро зовёт `explainShellWrites(command, { cwd, env,
dialect, mixed })`: те же цели, что `detectShellWrites` (её контракт — массив целей — прежний), и
`why[]` — до трёх коротких причин маркера `"?"` с токеном, из-за которого путь не вычислить, и
тем, что сделать («`$TMPDIR` нет в окружении хука — используй $TMP или абсолютный путь
временного каталога», «слово «"$T"» после timeout не вычисляется … — подставь значение
литералом»). Причины дописываются в отказ шага 6 и песочницы: «команда похожа на запись, но
путь не удалось определить: <причины> — …». Инцидент 2026-09-30: отказ токена не называл, и
агент не узнавал настоящую ошибку (`2>$null` в bash, `\"` в конце пути, незаданная переменная).
`mixed: true` — shell исполнителя неизвестен (Kilo на Windows: `action.dialects` — bash и
PowerShell), советы годятся обоим: для `$null` и `/dev/null` — «перенаправь в 2>&1 или убери
редирект» (`2>/dev/null` в PowerShell — путь `<диск>:\dev\null`, `$null` в bash — пустая
переменная), для `$TMPDIR` и переменной сессии PowerShell — «пиши путь литералом», без `$TMP` и
`$env:X`. Причина у Kilo идёт с префиксом диалекта (`bash: …`, `PowerShell: …`); причина из
вложенного интерпретатора (`bash -c`) уже начинается с его имени, второй префикс не ставится.

Цели записи:
- редиректы в файл: `>`, `>>`, `>|`, `&>`, `&>>`, `<>`, `>&файл`, `N>`, `N>>`, `N>&файл`;
  PowerShell `>`, `>>`, `N>`, `*>`. Не запись: POSIX — `/dev/null`, `/dev/stdout`,
  `/dev/stderr`; PowerShell — `$null`, `NUL`; в обоих — `>&N`, `>&-`, а также `<<<`
  (here-string — ввод, не запись). В POSIX `NUL` записью СЧИТАЕТСЯ: в Git Bash (msys) это
  обычный файл — `echo HELLOWORLD > NUL` создаёт в текущем каталоге файл NUL с этим
  содержимым (проверено запуском; до раунда 5, 2026-09-22, он считался псевдоустройством —
  ложное разрешение). В PowerShell 5.1 `> NUL` — устройство: Out-File падает «asked to open
  a device that was not a file», файла нет (проверено запуском);
- `sed -i`/`--in-place`, `tee`, `rm`, `rmdir`, `unlink`, `del`, `touch`, `mkdir`, `truncate`;
- `cp`, `mv`, `ln`, `install`: назначение — последний позиционный аргумент или `-t DIR`;
  у `mv` источники тоже (их не станет);
- `dd of=`, `find -delete`, `find -exec`, `find -fprint`;
- PowerShell: `Remove-Item`, `Set-Content`, `Add-Content`, `Clear-Content`, `Out-File`,
  `Tee-Object`, `Export-Csv`, `New-Item`, `Copy-Item`, `Move-Item` и их алиасы;
- то же внутри `$(…)`, `` `…` ``, `<(…)`, `>(…)`, тела heredoc с незакавыченным разделителем,
  `bash|sh -c '<скрипт>'`, `flock <файл> -c '<скрипт>'` (flock запускает строку через
  `${SHELL:-/bin/sh} -c`), `powershell|pwsh -Command`/`-EncodedCommand`, `eval`/`iex` строки-литерала,
  PowerShell `(…)`, `$(…)`, `{…}`.

Имя команды — basename без регистра и `.exe` на win32. После обёрток (`sudo`, `env`, `xargs`,
`git`, `timeout`, `then`, `do`, `time`, `setsid`, `flock`, `coproc`, `function`) команда —
следующее слово (у `flock` и `timeout` — после их позиционного аргумента). У `setsid` флаги
`-c/--ctty`, `-f/--fork`, `-w/--wait` значения НЕ имеют — это переключатели; у `flock`
`-c/--command <строка>` — не команда, а СКРИПТ, он разбирается как `sh -c` (формы `-c X`,
`-cX`, `-xc X`, `--command X`, `--command=X`: в группе коротких флагов `-c` не обязан быть
первым). Обеих утилит в Git Bash на этой машине нет (`command -v` пусто) — формы взяты из
util-linux setsid(1)/flock(1), запуском НЕ проверены; правило только расширяет детект записи.
`trap '<скрипт>' SIG` разбирается отдельно, в мире с неизвестным каталогом (ловушка
срабатывает позже). Нелитеральное имя команды — `"?"`, кроме имени через переменную на месте
команды: первое слово после присваиваний или слово после ключевого слова (`if`, `then`, `elif`,
`else`, `while`, `until`, `do`, `{`, `!`, `time`), переменная присвоена литералом в команде или
задана в окружении — тогда имя вычисляется (`R=rm; "$R" f` — запись `f`; инцидент 2026-09-29,
PulseProxy: `R="C:/…/rtk.exe"; "$R" --help` давал «?»). Имя, которое меняет переменные или
каталог shell'а (`read`, `export`, `cd`, `eval`, `source`, обёртки, `shopt`, `set`, `exec`…),
через переменную — `"?"`. Сразу после обёртки невычисленное слово — `"?"` с причиной: оно может
быть её флагом, аргументом или командой (`T=5; timeout "$T" rm f`, `F=-p; command "$F" rm f`,
`F=--; nohup "$F" rm f`, `A=X=1; env "$A" rm f` удаляют файл — проверено запуском Git Bash, ревью
2026-10-01).

Флаги:
- длинные опции GNU узнаются и по однозначному префиксу (`cp --t DIR`, `sed --in`);
- PowerShell: параметр — только незакавыченное слово, начинающееся с `-`, `–`, `—` или `―`
  и буквы; имя может быть префиксом (`-Fo`); `--` заканчивает параметры; неизвестный
  параметр делает целью каждое позиционное слово.

Каталог:
- пути возвращаются абсолютными от каталога, в котором shell выполнит запись;
- трекается только простая полностью разобранная форма `cd|pushd <один литеральный аргумент>`
  (POSIX, допустим `--`; в PowerShell — `cd|chdir|sl|Set-Location|pushd|Push-Location`
  с `-Path`/`-LiteralPath`); всё прочее, что меняет каталог, делает его НЕИЗВЕСТНЫМ, и
  относительные цели записи после этой точки — `"?"`;
- аргумент `cd|pushd`, начинающийся с `+` или `-`, — запись стека каталогов, а не каталог:
  `pushd +1` вращает стек и возвращает в прежний cwd (проверено запуском bash 5.2);
- cd может не удаться, и после `;`, перевода строки или `||` shell продолжит в прежнем
  каталоге — запись проверяется в обоих каталогах; только `cd X && …` оставляет один;
- POSIX-относительный каталог без `./` трекается, если в окружении или в команде нет `CDPATH`,
  в `BASHOPTS` нет `cdable_vars` и команда не вызывает `shopt`;
- `..` в каталоге cd даёт логический и физический (`set -P`) варианты — запись проверяется в обоих;
- Git Bash под Windows: `/c/…` — диск `C:`, прочие `/…` — каталоги самого Git, это `"?"`.

Heredoc (расхождение разбора с bash прячет команды, поэтому все правила проверены запуском):
- разделитель — обычное слово со снятием кавычек ПО ЧАСТЯМ: `<<E"O"F`, `<<E\OF`, `<<"EO"F`,
  `<<E\ OF` дают те же разделители, что `<<EOF`/`<<"E OF"`; закавычена хоть часть — тело
  без раскрытий. Разделитель, который сканер не воспроизводит буквально (`<<$X`, `<<$'E'`,
  `` <<`x` ``, незакрытая кавычка, перенос строки), — `"?"`;
- `<<` внутри `(( … ))` — арифметический сдвиг, а не heredoc: разбор отклоняется (`"?"`);
- `<<` внутри списка присваивания массива `a=( … )` — для bash синтаксическая ошибка: heredoc
  в очередь не ставится, следующие строки bash ВЫПОЛНЯЕТ. Разбор отклоняется (`"?"`).

Переменные:
- запоминаются `NAME=value` целым сегментом, `export`/`declare`/`typeset`/`readonly NAME=value`,
  PowerShell `$x = '…'`, `$env:X = '…'`; `NAME=value cmd` — только окружение команды;
- в путях раскрываются `$NAME`, `${NAME}`, `$env:NAME`, `$HOME`, ведущая `~`, `$PWD`
  (отслеживаемый каталог); PowerShell `$NAME` без присваивания пуст и НЕ равен `$env:NAME`;
- POSIX: ведущая `~` и `$HOME` — ОДИН источник, переменная окружения `HOME`; HOME
  присваивается в команде — путь неизвестен (`"?"`). Проверено запуском: bash следует `$HOME`
  и заданному в окружении вызова (`HOME=<dir> bash -c 'touch ~/a'` пишет в `<dir>`), и
  переназначенному внутри команды. HOME нет в окружении (процесс хука на Windows его не
  видит): `~` берётся из каталога пользователя процесса — bash в этом случае берёт его из
  passwd, и на этой машине это тот же каталог (проверено запуском); `$HOME` у bash пуст,
  поэтому у детектора он даёт `"?"`;
- переменная, которой где-либо в команде присваивают нетрекаемо (`read`, `for` не по списку
  литералов, `local`, `$((…))`, `${x:=}`, `S[0]=…`, `-OutVariable`, `[ref]`, `foreach`), неизвестна
  во всей команде;
- `for NAME in <литеральные слова>; do … done` на верхнем уровне сразу после плоского начала
  команды: у переменной цикла конечный набор значений, запись проверяется по каждому
  (`for d in a b; do rm -rf "$S/$d"; done` — цели `$S/a` и `$S/b`; инцидент 2026-09-30,
  ListeningGlass P3S1: такая очистка scratchpad отклонялась маркером). Переменная, которой уже
  присвоено в начале команды, так не трекается. Вложенному интерпретатору (`bash -c '…'` в теле
  цикла) значение из окружения хука для неё не передаётся — там она неизвестна (`"?"`): цикл
  переприсваивает и экспортированную переменную, прежнее значение было бы ложным;
  присваивание с динамическим именем (`declare "$n=…"`, `printf -v "$n"`, `(( $n = 1 ))`)
  делает неизвестными все переменные;
- незакавыченное POSIX-раскрытие с пробелом или шаблоном — `"?"`.

Арифметика и вложенные подоболочки. `(( … ))` и `$(( … ))` — арифметика: `>` и `<` там
операторы сравнения, а не редирект, и команд внутри нет. `((cmd) && cmd)` — вложенные
подоболочки, bash их ВЫПОЛНЯЕТ. Различаются они синтаксически, правилом самого bash, и разбор
его повторяет: команда `((` — арифметика, только если пара, открытая ВТОРОЙ скобкой,
закрывается непосредственно перед `)` (`parse_arith_cmd`); `$((` — арифметика, если содержимое
`$( … )` начинается с `(`, кончается `)` и скобки между ними сбалансированы (`chk_arithsub`).
Проверено запуском bash 5.2 msys: `((touch f))` и `echo $((touch f))` — «syntax error in
expression», файла нет; а `((echo x) > b)`, `((cd x) && (touch y))`, `echo $((ls) > c)` bash
выполняет, и их записи видны. Редирект ПОСЛЕ `))` (`(( n > 0 )) 2>err`) — настоящий.
Подстановки ВНУТРИ арифметики выполняются (`(( x = $(touch f) ))`) и разбираются. `#` внутри
`(( … ))` комментарием не считается (проверено запуском) — иначе признак арифметики уходил бы
за `))` и редиректы следующих команд пропадали. `<<` внутри `(( … ))` — по-прежнему отказ
разбора (`"?"`), чтобы тело heredoc не спрятало команды.

Шаблоны: в каталоге пути — `"?"`; в последнем компоненте — только у удаления и не с `.` или `[`;
`{a,b}` — `"?"`.

Маркер `"?"` даётся также при: неразобранной команде (незакрытые кавычки, подстановка, heredoc),
неизвестном каталоге, PowerShell-массиве и сплаттинге (`a ,b`, `@p`, `-Path:a,b`), невычисленном
слове, которое могло бы стать флагом (`cp "$o" a b`; обход — `cp -- "$f" dir/`), `cmd /c` с
командой записи, записи через .NET (`[IO.File]::Write…`, `.Delete()`), скрипте из пайпа
(`… | bash`) и при исключении внутри разбора.

Известные ложные отказы: heredoc, чей разделитель в тексте не встретился; `pushd -- +1` (для
bash это каталог `+1`); `cd|pushd <каталог> > <файл>` (переход происходит, но каталог считается
неизвестным — рядом с cd разрешено только псевдоустройство: POSIX `/dev/null`, PowerShell
`$null`, но не `NUL`, на котором PowerShell падает до выполнения команды); `(( touch <путь> ))`
и `(( rm <путь> ))` (для bash это арифметика, команда не выполняется, а путь показывается);
первое слово арифметики — подстановка (`echo $(( $(wc -l < f) + 1 ))`): оно считается
нелитеральным ИМЕНЕМ команды и даёт `"?"`.
Закрыто в раунде 5 (2026-09-22): `(( n > 0 ))` и `echo $(( 5 > 3 ))` фантомных целей `0`/`3`
больше не дают; `pushd <каталог> >/dev/null` каталога не теряет.

Границы разбора: содержимое чужих программ и скриптов не видно — `source`/`.` (делают каталог и
переменные неизвестными), `bash x.sh`, `pwsh -File`, `node -e`, `python -c`, `make`, `npm run`,
`curl -o`, `wget`, `tar -x`. Разбор линеен по длине команды: имена ищутся от границы слова,
иначе одно длинное слово давало O(n²) (24 000 букв — 4 с, 96 000 — 64 с), хук висел бы на
каждом вызове инструмента, а убитый по таймауту хук = allow (ревью C2 r3, 2026-09-22).

## 7. Алгоритм решения (`core.decide`)

Вход: `{ action, ctx }`, `ctx = { cwd, sessionId, role, event, run? }`.
Выход: `{ decision: "allow" | "deny", reason?, context?, updatedCommand? }`.

1. `root = findProjectRoot(cwd)`; нет корня → `allow` без текста (скоуп по каталогу).
2. `role === "executor"` → `allow` без текста. Роль: `WORKFLOW_RAILS_ROLE` из окружения;
   для Claude дополнительно — наличие поля `agent_id`/`agent_type` во входе хука
   (субагент; поле задокументировано в README как **не проверенное**, покрыто синтетическим тестом).
3. Загрузить состояние сессии. Нет состояния и нет `WORKFLOW_RAILS_SKILL` → **режим без скила**:
   единственный гард G0 — `edit|write` по realpath внутри `<root>/.workflow/src/skills/**`
   отклоняется: «правки скилов только через коуча на рельсах: `node .workflow/src/rails/cli.mjs start coach`».
   Остальное — `allow`.
4. Режим скила: загрузить `rails.yaml` и граф скила (кэш по mtime файлов в памяти процесса).
   Порядок проверок, первая сработавшая — итог:
   1. команда — вызов `cli.mjs` (`start|goto|status|reset|report|check|coverage|selfcheck`).
      Каждый сегмент (разделители `&&`, `;`, перевод строки) имеет вид
      `[WORKFLOW_RAILS_SKILL|WORKFLOW_RAILS_SESSION|WORKFLOW_RAILS_RUN=<литерал>] node <путь>/rails/cli.mjs <подкоманда> …`;
      присваивания допустимы только в POSIX, любое другое (NODE_OPTIONS, PATH, WORKFLOW_HOME…)
      делает команду не cli-вызовом. Интерпретатор — только `node`/`node.exe` без каталога
      (`.workflow/work/node …` запускал скрипт агента). В сегменте не более одного пайпа и
      только в фильтр-читатель (`| head -3`). Первым сегментом может идти `cd <dir>`; после
      `cd` допустимы `&&`, `;` или перевод строки, `||` — нет. Пачка `goto` — больше одного
      сегмента с подкомандой `goto` — `deny` с 1.25.0 (решение владельца 2026-10-03, после
      слияния цепочек правил: список проходит узлы, не выполняя их; один `goto` рядом с
      `status`/`report` разрешён). Иная такая команда → `allow`: в
      каждый cli-сегмент без `--session` перед первым `|` вставляется `--session <id>`
      (`updatedCommand`). `cli.mjs status && git commit` — не cli-команда, идёт по общим правилам.

      **Путь и каталог — только литералы** (проверено запуском 2026-09-22). Не годятся:
      раскрытия и подстановки (`$PWD/…`, `"$PWD/…"`, `${…}`, `$(…)`, `` `…` ``); `~` в начале, под
      bash и после `=`/`:`; символы `* ? [ ] { }` (Set-Location раскрывает шаблон и в `'…'`);
      `-` в начале; `:` не после буквы диска. `cd $PWD/.workflow/work/copy && node .workflow/src/rails/cli.mjs`
      резолвился от cwd, а shell запускал копию cli.mjs из write_scope. Под POSIX относительный
      каталог cd принимается только с `./` или `../` в начале, иначе bash ищет его по CDPATH.
      msys-путь Git Bash `/c/…` — это `C:/…`, но только в каталоге cd (его переводит сам builtin);
      путь cli.mjs вида `/c/…` — не cli-вызов. На win32 регистр сворачивается только у ASCII:
      `.wor\u212Aflow` (KELVIN SIGN) для NTFS — отдельное имя.

      Путь обязан вести к `<root>/.workflow/src/rails/cli.mjs` лексически или по realpath
      (`src/rails/cli.mjs` — только по realpath, раскладка workflowAi). Если после cd стоит не
      только `&&`, путь проверяется и от каталога cd, и от cwd вызова: при неудачном cd shell
      выполнит сегмент в прежнем каталоге.

      **`..` под POSIX** принимается, только если логический и физический подъём ведут в один
      каталог: каталог, из которого поднимаемся, — не ссылка, и родитель его realpath совпадает
      с realpath его текстового родителя. После `cd` в junction msys-bash отдаёт node.exe
      физический каталог (цель ссылки), и `cd ./lnk && node ../../../.workflow/src/rails/cli.mjs`
      запускал копию из цели. Ссылкой считается и то, что Windows видит не каталогом: ссылку
      Git Bash при `MSYS=winsymlinks:sys` Windows видит файлом с атрибутом System, при
      `winsymlinks:lnk` — файлом `.lnk`, а bash через неё переходит. Ошибка `lstat`/`stat`
      (в том числе несуществующий компонент) — тоже «неизвестно», то есть не cli-вызов.
      Короткие имена 8.3 и `/var → /private/var` ссылками не считаются. Под PowerShell на
      Windows `Set-Location` логический, node получает каталог ссылки — там `..` сверяется
      только по realpath свёрнутого пути.

      **Текст команды и CR.** Под PowerShell одиночный CR — разделитель statement'ов,
      `` ` ``+CR — буквальный CR в слове; под bash CR — символ слова, а msys-bash молча удаляет
      CR из текста. Поэтому canary, deny_shell, `stage_actions.match` и `detectShellWrites`
      проверяются и по тексту без CR (лишний отказ — допустимая цена). Под PowerShell не
      cli-вызов: команда, в тексте которой после снятия кавычек и бэктиков есть `--%`
      (stop-parsing: `-'-%'`, ``--`%``, `-""-%` …) или `` `u{ ``.

      **Переписывание `--quote "…"` в `'…'`** (ЗАДАЧА B2): только токен верхнего уровня
      cli-сегмента, значение — одна часть в двойных кавычках с неэкранированными `` ` ``/`$`

      `${…}` и бэктик перед настоящим переводом строки не переписываются. Переписанная команда
      обязана разбираться так же, как исходная, иначе остаётся как была.

## 8. Выходной слой

`output-check.check(text, config, state)` → `{ ok, missing[] }` по `output.final_requires`
и по положению: финальный ответ допустим только в `terminal` или `pause_nodes`.

Кроме требований есть запреты: `output.final_forbids` и `output.pause_forbids` — регулярки,
которые в ответе совпасть НЕ должны (элемент `missing[]` помечен префиксом `forbidden:`).
Нужны там, где инвариант скила — форма ответа, а не наличие строки: execute-task запрещает
перечислять пункты DoD и декларировать self-check в stdout. Битая регулярка в `forbids`
запрет не включает (иначе она глушила бы любой ответ), в `requires` — считается несовпадением.
Набор берётся по положению: в узле-паузе действуют `pause_*`, в терминале — `final_*`.

**Честная приостановка (2026-10-05, §15).** Ответ, начинающийся строкой
`RAILS_OUTCOME: blocked` или `RAILS_OUTCOME: needs_user` — отдельный исход из любого
узла: поля `ACTION:`/`REASON:`/`DONE:`/`REMAINING:` обязаны быть непустыми, `verdict=pass`
и дописанный RESULT со `status: pass` в нём запрещены. Валидная приостановка — не успех и не
терминал: `check` возвращает `outcome`, раннер проваливает попытку без повтора и без передачи
другому исполнителю, состояние и счётчики не меняются; ответ с невалидной приостановкой
(пустые поля, запрещённый PASS) проверку не проходит и ведёт к обычному повтору. Маркер в
середине чужого текста приостановкой не считается — только с начала ответа.

- Claude: хук `Stop`. Последнее сообщение ассистента читается из `transcript_path` (jsonl,
  последняя запись `type: "assistant"`, текстовые блоки). Нарушение → `{ "decision": "block",
  "reason": "…" }`, счётчик `stop_blocks:<node>` ≤ `max_stop_blocks`, дальше — `allow` с записью
  в журнал (`stop_block`, `exhausted: true`). Поле входа `stop_hook_active` (Claude Code ставит
  его на остановке сразу после блока) блок не снимает: прежде при `true` хук пропускал ответ, и
  `max_stop_blocks: 2` работал как 1 — прогон PulseProxy 2026-09-27, четыре сессии claude-haiku
  получили по одному блоку и закончили вне терминала. От цикла защищает счётчик узла: новый блок
  возможен только после перехода в узел с неисчерпанным счётчиком, повторный заход счётчик не
  обнуляет — за жизнь состояния блоков не больше `max_stop_blocks` × число узлов графа.
  Граница держится, только если счётчик лёг в файл состояния сессии (хук сверяет его после
  записи): запись упала или ушла в другой файл (в состоянии нет `session` или он чужой) — потолок
  один блок подряд, остановка с `stop_hook_active` проходит; в журнале `unsaved: true`.
  Отдельного потолка на сессию нет: он обрывал бы агента, который после каждого блока
  продвигается к терминалу. `start` и `reset` начинают состояние заново — счётчики с ним.
- Kilo и пайплайн: хука на финальный ответ нет. Раннер (§11) после завершения агента вызывает
  `check` по состоянию, найденному по `run`; при нарушении — один повтор с вердиктом: в той же
  сессии хоста, если её можно продолжить, иначе в новой (§11). Состояния нет при хуках на
  месте — тоже нарушение (§11).

## 9. Адаптеры

### 9.1 Claude Code — `claude-hook.mjs`

Регистрируется на события `PreToolUse` (все инструменты), `PostToolUse`, `Stop`,

|---|---|
| PreToolUse | `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"…"}}` либо `allow` (пустой вывод), либо `updatedInput` с изменённой командой для инъекции `--session` |

| Stop | `{"decision":"block","reason":"…"}` или пустой вывод; потолок — `max_stop_blocks` на узел, `stop_hook_active` блок снимает, только если счётчик не сохранился (§8) |

Поля входа, проверенные канарейкой 2026-09-21: `session_id`, `transcript_path`, `cwd`,
`permission_mode`, `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`, `prompt_id`.
Отказ в режиме `-p` через проектный `settings` подтверждён.

| `report --days N [--skill X] [--journal <файл\|каталог>]` | сводка журнала: отказы по узлу, узлы с ≥3 повторами в одной сессии, потолки, сбросы, Stop-блоки, канарейка отдельной строкой (проверка живости, не отказ — §7 п.4.2), ошибки хука; `--journal` — вместо журнала проекта файл или все `*.jsonl` под каталогом (например, `tests/cases/<TC>/current`) |
| `check --skill X \| --all` | валидация графа и rails.yaml; статистика; код выхода 1 при ошибках |
| `coverage --skill X --baseline <git-ref> [--map <file>]` | покрытие инвариантов (§12); карта по умолчанию — `rails-migration.yaml` скила; код выхода 1 при пропусках или ненайденной `--map` |
| `selfcheck` | регистрация: `.claude/settings.local.json` содержит хуки rails с существующими путями, `.kilo/plugin/workflow-rails.js` существует, `rails.yaml` каждого скила с графом валиден |

Канарейка живости — не команда CLI, а узел графа: агент в первом этапе выполняет `canary`
и обязан получить отказ; если команда выполнилась — рельсы выключены, агент останавливается
и сообщает человеку.

## 12. Покрытие при конверсии (`coverage`)

Гарантия «ничего не утрачено» при переводе прозы в граф. Из базовой версии скила
(`git show <ref>:src/skills/<skill>/SKILL.md` и `workflows/*.md` — только эти файлы,
справочники в граф не переносятся) извлекаются **фразы-инварианты**: предложения из
строк, содержащих `⛔`, `⚠️`, `**…**`, даты (`\d{4}-\d{2}-\d{2}`, `\d{2}\.\d{2}\.\d{4}`),
а также строки таблиц под заголовками маршрутизации, загрузки и шаблонов (заголовок
секции содержит «маршрутизац», «загрузк» или «шаблон»), без строки-шапки. Фраза
нормализуется (как лейбл, §3, плюс снятие `` ` ``, маркера списка и `>`) и считается
покрытой, если её подстрока длиной ≥ 25 символов встречается в текущих файлах скила
(все `*.md` кроме `tests/`, плюс `rails.yaml`) **или** покрыта картой `--map`.
Карта — `rails-migration.yaml` рядом с `SKILL.md`: либо плоский объект `phrase: target`,
либо `entries: [{phrase, target}]` с метаданными (`version`, `skill`, `baseline`);
`phrase` — отличительный фрагмент (≥ 10 символов), совпадает с инвариантом целиком или
входит в него подстрокой; `target` — узел, файл или `dropped: <обоснование>`.
Без `--map` берётся `rails-migration.yaml` скила, если он есть. Относительный `--map`
ищется от текущего каталога, затем от каталога скила; явно заданной карты нет ни там, ни
там — ошибка, код выхода 1 (раньше пустая карта подставлялась молча: 151/200 вместо
200/200, прогон 2026-09-22). Взятая карта печатается строкой `Карта:`.
Непокрытые фразы печатаются списком; код выхода 1.

## 14. Границы (честно)

Принуждается то, что видно в аргументах вызова инструмента или в тексте ответа.
Гард по тексту команды обходится косвенностью (переменная, alias, скрипт-обёртка) — он ловит
небрежность, не намеренный обход. Качество evidence, изоляция формулировок, коррекция
стейкхолдера — остаются текстом узлов графа. Разбор mermaid ведётся собственным парсером
подмножества, не официальным.

**Границы короткого замыкания cli-вызова и разбора shell (2026-09-22).**

- Проверка «cli.mjs этого проекта» опирается на `ctx.cwd` адаптера. У Claude Code `cwd` во
  входе PreToolUse — текущий каталог сессии; Bash-инструмент обновляет его после каждой
  команды переднего плана с `cd` (фоновая не меняет). Прочитано во встроенном JS claude.exe
  2.1.278, запуском не проверено. Kilo-адаптер берёт `cwd = directory` проекта и не видит
  аргумент `workdir` bash-инструмента Kilo.
- Окружение пользователя в модель не входит: `CDPATH`, относительные элементы `PATH`,
  alias/функции `cd`/`node` из профиля, `MSYS2_ARG_CONV_EXCL`/`MSYS_NO_PATHCONV`, нестандартный
  cygdrive-префикс. Агент не может задать их внутри cli-команды, но они меняют, куда перейдёт
  `cd` и какой файл запустит node.
- Ложные отказы короткого замыкания (команда идёт по общим правилам, без `--session`): `cd -`,
  `cd ~`, путь с `[ ] { } * ?`, `node` с каталогом, PowerShell `--%`, msys-пути кроме
  `/<буква>/…`, префиксы окружения вне списка, CR в тексте команды под bash, `..` через
  junction/symlink/msys-ссылку или через несуществующий каталог. Пишите
  `cd "<абсолютный путь>" && node .workflow/src/rails/cli.mjs …` или путь без `..`.
- PowerShell 5.1 не знает `&&`. После `cd <dir>;` путь обязан вести к cli.mjs проекта и от
  каталога cd, и от `ctx.cwd`, поэтому из подкаталога `cd "<root>"; node .workflow/src/rails/cli.mjs …`
  — не cli-вызов. Обход — абсолютный путь к cli.mjs.
- Точность доставки `--quote` ограничена маршалингом аргументов native exe на Windows: значение
  с буквальной `"`, хвостовыми `\` или вложенным `C:\…` может дойти до node.exe искажённым —
  одинаково для исходной и переписанной команды, выполнения это не даёт. Лейбл, оканчивающийся
  бэктиком, нельзя взять в `"…"` под PowerShell — берите `'…'`.
- Разбор записи из shell ловит небрежность, а не намеренный обход: содержимое скриптов и чужих
  интерпретаторов не видно (§6), а гард по тексту команды обходится косвенностью.

## 15. Физическая политика целей, закреплённый рантайм, честная приостановка (2026-10-05)

Дедлок коуча 2026-10-05: правка скила была привязана к этапу П4, а канон закрыт — сессия,
дошедшая до законного отказа вне П4, больше не могла ни править, ни завершиться. Решение —
развести редактируемую локальную копию и полномочия действующего запуска.

### 15.1 Классификация физических целей (`write-policy.mjs`)

`classifyWrites(root, targets, kind, cwd, callerSkill)` вызывается из `decide` для действий
`edit`/`write` и для shell-команд с распознанными целями записи (редирект, `cat >`) — до
разрешения роли executor и до правил режима скила: иначе shell-редирект в канон обходил бы
защиту (ревью 2026-10-05). Ошибка классификации —
типированная `WritePolicyError` с `railsFailClosed: true`: `decide` отвечает deny, а не
«снимаю рельсы». Цели-маркеры «?» не классифицируются — их, как раньше, ведёт слой режимов.
Независимую копию открывает только авторизованный скил (`authoritative_skills`, по умолчанию
коуч): sessionless-вызов (executor) получает отказ классификатора, у сессии чужого скила
shell-запись в дерево скилов остаётся за правилами её режима.

Классы целей (все — по `realpath`, существующие и будущие файлы):

| Класс | Условие | Решение |
|---|---|---|
| Канон | внутри `realpath` каталога скилов установки (`src/skills` рядом с ядром) или корня из `canonical_skill_roots` внешней политики | deny «каноническая цель защищена», кроме точного совпадения с maintenance |
| Protected | файл внешней политики, хранилище снимков `state/rails-runtime`, каталог состояний `state/rails` | deny всегда, maintenance его не открывает |
| Инфраструктура | каталог самого ядра rails установки | как канон |
| Независимая локальная копия | `<root>/.workflow/src/skills/<name>/…`: каталог существует или `<name>` — ещё не созданный скил (запись внутрь его будущего каталога, mount — обычный и не ведёт в канон); всё дерево — обычные каталоги/файлы без symlink/junction и файлов с `nlink > 1`, физически внутри корня проекта, вне канона | цели попадают в `unrestricted` |
| Прочее | всё остальное | без изменений, ведут правила режима |

Последствия `unrestricted`: для этих целей пропускаются `write_deny` и проверка
`write_scope`; из правил `stage_actions` unrestricted-цели исключаются только у команд
`edit`/`write` — shell-команда со своими целями сопоставляется с ними как прежде. Копия
(целями `edit`/`write`) правится на любом этапе.
Смешанная операция с канонической целью отклоняется, кроме точного maintenance на неё;
цель protected отклоняется всегда. Файл с общим inode (hardlink) — deny без точного
maintenance: `realpath` его не раскрывает, и алиас-запись могла бы править канон
(ревью 2026-10-05, второй раунд). Роль executor не открывает канон — классификация
отказывает до разрешения роли. В режиме G0 (нет сессии и `WORKFLOW_RAILS_SKILL`)
классификация не вызывается: правки скилов отклоняет сам G0-гард «только через коуча»
(он смотрит только `edit`/`write`, shell им не ведётся вовсе).

### 15.2 Внешняя политика владельца (`.workflow/rails-policy.yaml`)

Опциональный файл рядом с состояниями; отсутствует — действуют значения по умолчанию
(канон установки, protected-пути). Существует — обязан быть `version: 1`, иначе fail closed.
Поддержание (`maintenance`) — точные абсолютные пути без wildcard и обязательный срок
`expires_at`; истёк срок — разрешений нет. Поддержание не может разрешать запись самой
политики и состояний runtime.
Файл и хранилище снимков обязаны быть обычными файлами/каталогами (не ссылками).

### 15.3 Закреплённый рантайм (`runtime-snapshot.mjs`)

`loadSkillRuntime(root, skill, state)` при переданном состоянии сессии отдаёт config и граф
из снимка, а не из живых файлов скила. Личность запуска — `{root, session, skill, run,
started}`, снимок — `state/rails-runtime/<sha256 личности>.json` (создание `wx`, отказ по
`EEXIST` перечитывает готовый), в состоянии — привязка `runtime: {version, id, hash}`.
Привязка уже есть, а снимок повреждён/отсутствует — fail closed без перечитывания исходников;
раннер в этом случае завершает попытку `RAILS_RUNTIME_LOST` — без повтора и без передачи
другому исполнителю, как и `RAILS_SUSPENDED`.
Ответ — свежие объекты: мутации возвращённого config/графа хранилище не меняют.

Правка живых `rails.yaml`/графа/`SKILL.md` локальной копии меняет будущие запуски, не текущий.
Границы активации: `cli start` закрепляет рантайм сразу; повторный `start` того же скила —
идемпотентный resume (узел, история, счётчики и привязка сохраняются); `start` другого скила и
`reset` поверх закреплённого запуска отклонены — новый запуск открывает владелец, а не `--force`
и не сброс состояния. CLI/hook/kilo/раннер читают рантайм только через привязку состояния.

### 15.4 Строгое состояние (`state.mjs`)

`loadState`: файла нет (ENOENT) → `null`; файл есть, но не читается/не JSON/не проходит
проверку формы → `StateError` с `railsFailClosed` (версия, совпадение `session` с именем файла,
`skill`/`node`, времена, история, неотрицательные счётчики, форма привязки runtime).
Хуки и CLI показывают это как deny/block, а не как «сессии нет».

### 15.5 Безопасное отделение копии (`junction-manager.mjs`)

`ejectSkill`/`ejectConfigs`/`ejectScripts`: сначала полная копия источника в соседний
временный каталог (`dereference`), сверка — число файлов и байт совпадают, в копии нет ссылок
и файлов с `nlink > 1`; только потом объект ссылки заменяется копией (unlink ссылки + rename,
без рекурсивного удаления цели). Сбой подготовки — временный каталог убирается, ссылка не
тронута; сбой переключения (ссылка уже снята) — цель ссылки, считанная до удаления через
`readlink`, восстанавливает ссылку, временная копия сохраняется для повтора; если и
восстановление не удалось, копия остаётся по временному пути. Цель, не являющаяся ссылкой
(копия уже отделена), не перезаписывается.

Тесты: `src/tests/rails-write-policy.test.mjs`, `rails-runtime-snapshot.test.mjs`,
обновлённые `rails-core`/`rails-cli*`/`rails-claude-hook*`/`rails-kilo-plugin*`/`rails-state`/
`rails-output-check`/`run-skill-tests`/`runner-rails-retry`/`junction-manager`, гарды коуча
`h1`/`h3` ( fixture `_project.mjs` различает junction на канон и независимую копию).
## 16. Штатный выход из роли: подтверждение завершения и разрешение владельца (2026-10-06)

Дефект: «Адъютант» (сессия коуча 2026-10-05/06, workflowAi) дошёл до терминального узла P8S2,
Stop-лимит исчерпался, положительный результат проверки финального ответа нигде не сохранялся,
а `reset` закреплённого запуска отклонён безусловно — сессия оставалась под рельсами навсегда,
и ни один штатный путь не возвращал ей нейтральный режим. Терминальный узел и разрешённый Stop
завершением не считаются: Stop разрешает остановку и после исчерпания потолка блокировок.

### 16.1 Подтверждение завершения (`completion.mjs`)

`recordCompletion({root, state, source, answer|transcriptPath})` — доверенная проверка
финального ответа по закреплённому runtime и запись `state.completion` (с сохранением
состояния и записью `type: "completion"` в журнал). Все условия обязательны, первое
нарушенное — отказ без записи:

- runtime закреплён, привязка соответствует личности запуска (`{root, session, skill, run,
  started}` → `runtime.id`), snapshot цел — повреждение отказывает, не перекрепляет;
- узел в `config.terminal` (по снимку); узел паузы подтверждения не создаёт;
- ответ не пуст и проходит выходной слой снимка; приостановка `RAILS_OUTCOME:
  blocked|needs_user` — не завершение (работы ждут владельца), подтверждения не даёт.
  Завершённый отрицательный `verdict` — завершение процедуры: значение строки
  `verdict = …` записывается в подтверждение; успешность продукта — не его забота.

Источники: `stop-hook` (Stop-гейт при положительной проверке в терминале — с этого момента
«pass» сохраняется сам), `cli-transcript` (`complete --transcript` — исторический ответ:
последнее сообщение ассистента из transcript сессии; файл обязан принадлежать сессии — имя
`<sessionId>.jsonl` и `sessionId` в записях), `runner` (проверенный ответ стадии).

Подтверждение хранит хеш ответа и хеш существенного состояния (`essentialStateDigest`:
скил, узел, run, started, счётчики, отказы, флаги, длина истории и последний переход,
привязка runtime; `updated`/`dedupe` не входят). Изменение существенной части после
подтверждения делает его устаревшим — `verifyExit` отказывает до выпуска разрешения.

### 16.2 Разрешение владельца и `exit`

Само подтверждение ничего не разрешает. Выход требует файла разрешения, который владелец
создаёт сам вне инструментов агента (запись в защищённый каталог состояний закрыта
классификатором и ролям executor, и shell-записям — §15.1); CLI разрешений не создаёт,
отказ `exit` печатает путь и шаблон. Файл — `state/rails/.exit-grant-<sessionId>.json`
(имя с точкой: перечень сессий проекта его не подбирает):

```json
{"version":1,"session":"<id>","completion_sha256":"<хеш state.completion>","expires_at":"<ISO>"}
```

`performExit` проверяет всё по новой, затем одноразово потребляет разрешение
(переименование в `*.used` — у параллельного выхода исходник уже исчез) и создаёт
**маркер завершения** — отдельный файл `state/rails/.completed-<sessionId>.json`
(`{version, session, t, completion_sha256, grant_expires_at}`). У состояния много
писателей (хуки, CLI, раннер), у маркера один — exit: конкурирующая запись состояния
не может его стереть. Создание `'wx'`, повреждённый или чужой маркер — `StateError`
(fail closed). Отказ маркера после потребления разрешения — запись `error` в журнал,
владелец перевыпускает: повторное использование разрешения дешевле его «возврата».
Просроченное, чужое, привязанное к другому подтверждению — отказ. Состояние, история,
счётчики, привязка runtime и журнал сохраняются целиком; `reset` завершённой сессии
отклонён так же, как закреплённой.

После отметки сессия в нейтральном режиме: Stop не проверяет и не блокирует, PreToolUse
не ведёт сессию и не пересоздаёт состояние из `WORKFLOW_RAILS_SKILL` (действует G0 —
правки скилов только через коуча), SessionStart и UserPromptSubmit подсказок роли не
дают, PostToolUse/kilo-плагин узел не называют. `start` (любой скил, и с `--force`),
`goto` и `reset` поверх завершённой сессии отклонены — старый запуск не перезаписывается,
новый открывает владелец новой сессией; роль из окружения хоста не возвращается.

Детали жёсткости (ревью 2026-10-06, круги 2–14): потребление разрешения и маркер идут
под файл-замком `.exit-lock-<sessionId>` — атомарный эксклюзивный клейм ('wx'), в
файле pid владельца. ПОХИЩЕНИЯ КЛЕЙМА НЕТ: код никогда не удаляет и не перемещает
чужой клейм — любая кража (даже «мёртвого») открывала гонку с живым владельцем, чей
клейм успел смениться на пути (доказано ревью на кругах 8–13). Взаимное исключение
поэтому абсолютное: защищённые действия (потребление разрешения, маркер, сохранение
снятия) выполняет только владелец клейма, перепроверяя содержание на каждом шаге;
паузы процесса ничего не открывают. Клейм мёртвого или зависшего владельца снимает
человек: `exit` называет pid и путь файла; инвалидация в этой ситуации даёт видимый
сбой (attempted без traced — Stop блокирует остановку). Пид, переиспользованный
посторонним живым процессом (как и нечитаемый файл замка), — консервативный busy до
ручного удаления. Маркер создаётся на перечитанное состояние и только при целом
подтверждении и чистом следе; если инвалидация вклинилась в момент выхода — маркер
снимается обратно, выход не состоялся, владелец перевыпускает разрешение. Сбой
снятия подтверждения оставляет надгробие `.invalid-<sessionId>.json` и журнальную
ошибку с хешем подтверждения: `exit` по неснятому подтверждению не проходит, пока
инвалидация не повторится удачно; след другого (устаревшего) подтверждения не
блокирует. Принадлежность transcript — не «первая попавшаяся запись»: нужна хотя бы
одна запись с `sessionId` сессии, чужая запись в середине файла даёт отказ; ответ и
проверка читаются один раз. Пустое последнее сообщение ассистента — тоже новый
исход: прежнее подтверждение снимается, как и при непроходном ответе и при
приостановке.

Тесты: `src/tests/rails-completion.test.mjs` (подтверждение: терминал/пауза/приостановка/
повреждённый runtime/устаревание; complete: свой-чужой transcript; exit: чужое, просроченное,
несовпадающее, одноразовость; нейтральность после выхода; защита файла разрешения; журнал),
обновлённые `rails-state`, `rails-cli*`, `rails-claude-hook*`, `runner-rails-retry`.

Границы (честно, как §14): подтверждение строит тот же код, который исполняет агент, —
механизм отличает штатный путь от сбоя, но не криптография против намеренного обхода:
всё, что агент делает, видно в журнале (`completion`, `exit`, отказы), а запись в
защищённый каталог вне инструментов агента остаётся актом владельца.
