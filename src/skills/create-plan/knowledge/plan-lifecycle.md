# Жизненный цикл статусов плана

Каждый план проходит через определённые статусы. Скил `create-plan` должен знать их, чтобы корректно устанавливать начальный статус и не использовать невалидные значения.

## Статусы

```
draft → approved → active → completed → archived
```

| Статус | Описание | Кто устанавливает |
|--------|----------|-------------------|
| `draft` | Черновик. План создан, но ещё не утверждён стейкхолдером | Скил `create-plan` при создании |
| `approved` | Утверждён стейкхолдером. Готов к декомпозиции на тикеты | Стейкхолдер после ревью плана |
| `active` | В работе. Тикеты созданы и прошли машинную проверку атомарности | Pipeline: стадия `verify-atomicity` при `status: passed` (не декомпозитор) |
| `completed` | Все тикеты плана завершены | Pipeline после завершения всех тикетов |
| `archived` | Архивирован. Перемещён в `plans/archive/` | Скрипт/команда архивации проекта |

## Правила для скила create-plan

1. **Всегда создавай план со статусом `draft`** — план должен пройти ревью и утверждение стейкхолдером
2. **Не ставь `approved` автоматически** — утверждение делает стейкхолдер
3. **Не ставь `active`** — этот статус устанавливается после декомпозиции

## Связь с pipeline

Скрипт `check-plan-decomposed.js` сканирует планы в `plans/current/` и отправляет на декомпозицию **только** планы со статусом `approved` без тикетов. Планы в `draft` пропускаются.

Это значит: пока стейкхолдер не утвердит план (`status: approved`), pipeline **не будет** его декомпозировать.

**Переход `approved → active`** выполняется стадией `verify-atomicity` пайплайна (скрипт скила декомпозиции), **не** декомпозитором и **не** скилом `create-plan`. Условие перехода: все тикеты плана прошли машинную проверку атомарности (`status: passed`). Если атомарность упала и счётчик попыток `atomicity_check_attempts` достиг `max: 3` — план остаётся в `approved`, в работу не уходит; стадия `increment-atomicity-counter` передаёт управление в `check-conditions` без активации плана.

## Правка утверждённого плана

План в `approved` или `active` правит стейкхолдер или сессия вне пайплайна. Что делать с тикетами, зависит от того, когда сделана правка:

| Когда | Что сделать с тикетами |
|-------|------------------------|
| `approved`, тикетов плана ещё нет | ничего: стадия декомпозиции прочитает новый текст |
| Идёт декомпозиция | стадия читает план в начале и правку, внесённую после чтения, может не увидеть: после стадии сверь тикеты изменённой задачи с новым текстом и приведи их к нему |
| Тикеты созданы — план `approved` в ожидании проверки атомарности или `active` | пайплайн правку к тикетам не переносит: `check-plan-decomposed.js` на декомпозицию отправляет только план без тикетов, а повторный проход по отказам атомарности правит лишь тикеты из списка отказов. Тикет вне `done/` меняется той же правкой — описание и пункты DoD дословно по новому тексту задачи вместе с её записями проверки; для тикета в `done/`, результат которого правка меняет, заводится новый тикет; новая задача получает тикет явно |

Каждая правка — строка «Истории изменений» плана: дата, автор, номера изменённых задач и ID затронутых тикетов. Правку, которая меняет цель или scope, утверждает стейкхолдер.
