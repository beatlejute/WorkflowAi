# Обоснования стоп-гейтов декомпозиции

Не нормативная часть — только «почему». Нормы, пороги и порядок действий — в `workflows/decompose.md` и `knowledge/atomicity-checklist.md`.

## 9.A — дословный перенос формулировок критериев

**Антипаттерн «тихий семантический drift»:** сглаживание длинной формулировки критерия плана до короткой «общего смысла» в тикете, с удалением уточнений в скобках/отрицаний как «косметики», уничтожает отличительный признак критерия и превращает приёмку в тавтологию (исполнитель честно проходит ослабленную формулировку, реальный критерий плана остаётся невыполненным). Уточнение в скобках/после тире почти никогда не косметика.

**Почему это стоп-гейт:** после записи тикета формулировка расходится по цепочке (реализация → ревью → приёмка) на ослабленной версии; исправление задним числом требует переоткрытия тикета — дешевле сверить один раз перед записью.

## 9.B — `id_ranges` как единственный источник нумерации

Историческая причина: норма «вызови `get-next-id.js`» держалась на дисциплине агента; fallback-модели с коротким окном игнорировали её и стартовали с 001, коллизируя с архивными ID (подтверждено инцидентом при отказе основной модели). Архитектурный принцип: решение про ID принимает инфраструктура (стадия `allocate-ticket-ids`), агент не может «забыть» — альтернативы нет. Коллизия с архивом/done невозможна by design: `allocate-ticket-ids` сканирует все поддиректории `.workflow/tickets/` до декомпозиции.

**Антипаттерн:** «возьму номера из головы, раз скрипт не вызывается напрямую» — единственный источник `id_ranges`; отклонение ломает ссылочную целостность (`depends_on`, `parent_plan` уже ссылаются на записанный ID).

Формат — строка, не объект: при подстановке `$context.*` runner превращает объекты в `[object Object]`, а скалярные строки подставляются корректно.

## 9.C — реестр capabilities

Тикет с изобретённым capability физически неисполним — пайплайн блокирует по `no_capable_agent`, цикл retry → blocked расходует слоты и блокирует весь план. Дешевле сверить с реестром один раз перед записью, чем чинить задним числом.

## 9.1 п.4 — пре-валидация ID до записи

`Write` по занятому пути молча перезаписывает чужой тикет; проверка после сохранения уже не увидит коллизию (совпадение останется ровно одно).

## Проверка 7 атомарности — отдельная проверка

Разные пункты DoD могут проверять «одно и то же» семантически, но исполняться разными исполнителями в разных сессиях/стадиях — кросс-исполнительская зависимость делает тикет невыполнимым за одну сессию, даже если смысловое ядро одно.
