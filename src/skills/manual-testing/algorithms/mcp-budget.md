# Алгоритм: Бюджетирование MCP-сессии

Формализованный расчёт и контроль расхода MCP-вызовов на тестовую сессию.

## Вход

- Бюджет MCP-вызовов из `context.notes` тикета (или значение по умолчанию: 80)
- Количество тест-кейсов (TC) в скоупе
- Тип тестирования (smoke, regression, exploratory)

## Формула распределения

```
avg_cost_per_TC = 10        # дефолт; если context.notes задаёт значение — оно приоритетно
setup_reserve   = 5         # Quick-start checklist (3-4 вызова + запуск приложения)
safety_margin   = 0.1       # 10% резерв на непредвиденные ситуации

effective_budget = budget - setup_reserve
max_TC_per_session = floor(effective_budget * (1 - safety_margin) / avg_cost_per_TC)
```

**Пример:** бюджет = 80 → effective = 75 → max_TC = floor(75 × 0.9 / 10) = **6 TC за сессию**.

**Быстрый расчёт (setup 5, margin 10%):** 50→4, 80→6, 100→8, 140→12 TC.

## Правила

### Планирование continuation

Если тикет содержит больше TC, чем `max_TC_per_session`:

1. **Перед началом** запиши в тикет: «Запланирована continuation: TC-001..TC-006 в сессии 1, TC-007..TC-010 в сессии 2»
2. Выполняй TC по приоритету: быстрые (Snapshot + визуальная верификация, 2-3 MCP-вызова) → действие+проверка (4-6) → длительные с ожиданием (6-10). Чем дольше TC — тем выше риск MCP disconnect
3. **После первых 2 TC** пересчитай `avg_cost_per_TC` по фактическому расходу и `max_TC_per_session`; при расхождении с планом — обнови continuation в тикете
4. После завершения `max_TC` — зафиксируй прогресс и заверши сессию

### Checkpoint accounting

В начале каждого TC записывай номер текущего MCP-вызова:

```
TC-001 starts at call #6 → done at call #14 (8 calls)
TC-002 starts at call #14 → done at call #22 (8 calls)
TC-003 starts at call #22 → done at call #35 (13 calls) ← ПРЕВЫШЕНИЕ
```

Это даёт данные для калибровки `avg_cost_per_TC` в будущих сессиях.

### Жёсткий порог BLOCKED

- **TC > 12 MCP-вызовов = BLOCKED**, без исключений
- Зафиксируй: что наблюдалось, на чём застрял, сколько вызовов потрачено
- Переходи к следующему TC

### Rabbit hole detection (Explicit Intent)

**Источник:** Advanced Tool Calling in LLM Agents (sparkco.ai, 2025)

Перед каждым **не очевидным** инструментальным вызовом задай себе вопрос: «Зачем именно этот вызов и что он подтвердит в рамках текущего TC?» Если ответ не формулируется за 1 строку — это сигнал rabbit hole.

```
Текущее действие входит в шаги TC?
├── ДА → продолжай
└── НЕТ → это rabbit hole
    ├── Расследование инфраструктуры (Get-ChildItem, Test-Path, Get-Acl) → СТОП
    ├── Создание собственных инструментов (HTTP-клиент, скрипт обхода) → СТОП
    ├── Установка/запуск продукта из CLI при UI-тестировании → СТОП
    ├── Цель — «разобраться как работает X» → СТОП
    ├── Третий подряд вызов без видимого прогресса → BLOCKED, зафиксируй и переходи к следующему TC
    └── Другое: задай вопрос «это в скоупе TC?» — если нет → BLOCKED
```

### Экономный режим

**Активация:** потрачено >50% бюджета И выполнено <50% TC (Budget Guard, `workflows/smoke.md` → 3a) ИЛИ осталось <30% бюджета ИЛИ 2+ MCP disconnect в сессии.

При активации:
1. **Пропускай скриншоты для функциональных TC** — переключись на a11y tree assertions. **Исключение:** для TC с визуальными критериями (SKILL.md, принцип 8) скриншот остаётся обязательным — a11y tree не содержит визуальных свойств, и без скриншота такой TC невозможно проверить
2. **Записывай конкретное значение** из a11y tree для каждого TC (не только PASS/FAIL, а точный текст из Snapshot: `a11y: "Saved" found in status region`)
3. **Data assertion ценнее visual evidence** — первый обнаруживает баг, второй лишь фиксирует состояние

Дополнительно: минимум Snapshot, пропуск длительных TC, OBSERVATION вместо полного расследования.
