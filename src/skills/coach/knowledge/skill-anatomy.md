# Эталонная анатомия скила

Справочник по структуре и содержанию скила workflow-ai на рельсах. Единственная поддерживаемая форма — графовая (`knowledge/rails-concept.md`). Скил в прозаической форме (секции и нумерованные шаги без графа и `rails.yaml`) — не на рельсах: аудит выдаёт CRITICAL и обязательный CONVERT (`algorithms/graph-conversion.md`).

## Обязательная структура директорий

```
skill-name/
├── SKILL.md              # Frontmatter + граф ядра (mermaid): роль, правила, маршрутизация, самопроверки, отчёт
├── rails.yaml            # Гарды: область записи, запреты, действие-по-этапу, потолки, выходной слой
├── rails-migration.yaml  # Карта переноса фраз-инвариантов (появляется после CONVERT)
├── README.md             # Документация для людей
├── workflows/            # Фрагменты графа — по одному на ветку (тип работы), этапы 10, 20, …
├── knowledge/            # Экспертные знания домена — справочники, не цитируются
├── algorithms/           # Формализованные методы принятия решений
├── templates/            # Шаблоны вывода
└── tests/
    ├── index.yaml        # target_agents[], список кейсов
    ├── cases/ rubrics/ fixtures/   # регрессионные тесты скила (L0 / L1 / L2)
    └── rails/            # тест на каждый гард из rails.yaml
```

На уровне проекта, рядом со скилами (не внутри skill-name/): `shared/README.md` — индекс, `shared/module.md` — межскиловые модули (см. «Shared Knowledge»).

## SKILL.md — обязательные компоненты

| Компонент | Критерий качества |
|-----------|-------------------|
| **Frontmatter** (name, description, ticket_prefix, rails) | description 2–3 предложения, prefix уникален, `rails: rails.yaml` |
| **Преамбула** | 3–6 строк: как читать граф, где фрагменты, где грамматика. Прозы, дублирующей узлы, нет |
| **Этап 0 — вход и правила роли** | `E` с ролью исполнителя; `R`: «делает / не делает», объекты работы, запреты (конкретно, без абстракций); `S`: канарейка живости, чтение входов, каноническая строка shared; `Q`: маршрутизация — **только собственные типы работы**, триггеры в лейбле, ребро на `E` каждой ветки, fallback «тип не определяется — …» |
| **Этапы работы** | `R`/`S`/`G` по существу: сбор данных → работа → самопроверка; каждый `G` возвращает назад и имеет потолок в `cycles`; гейт перед каждым необратимым действием |
| **Этап отчёта** (последний) | `R`: формат вывода, специфичный для домена; `S`: обязательные строки ответа (`RAILS:`, `verdict=`, `Файлы:`), остановка; узел в `terminal` |
| **Узлы загрузки** | каждый файл `knowledge/`, `algorithms/`, `templates/` упомянут узлом с условием загрузки |
| **Принципы** | 3–7 `R`-узлов, actionable, не декларативные, с датой и ценой инцидента там, где правило выросло из инцидента |
| **Границы компетенции** | в `R` или терминальном `S`: смежные зоны с указанием, куда направить |

## Фрагменты `workflows/*.md`

| Требование | Критерий |
|------------|----------|
| Заголовок и 1–2 строки прозы | этап, откуда вход, куда выход; больше прозы нет |
| Один mermaid-блок | все узлы одного этапа (10, 20, …); номера этапов не пересекаются между файлами |
| Шаги | `S`-узлы с глаголами, ссылки на knowledge/algorithms в лейблах, пороги числами |
| Завершение | `G` с потолком либо прямое ребро в узел ядра (черновик, тест, отчёт) |
| Вход ветки | ребро из `Q` маршрутизации этапа 0 |

## `rails.yaml` — обязательные секции

| Секция | Назначение |
|--------|------------|
| `entry`, `terminal`, `pause_nodes` | вход, узлы финального ответа, узлы вопроса стейкхолдеру |
| `write_scope`, `write_deny`, `allow_temp` | область записи скила; запрет на свой `rails.yaml`, `tests/rails/` и ядро rails |
| `deny_shell`, `deny_mcp` | запреты по инцидентам — каждый с `reason` и `incident` |
| `stage_actions` | действие только на своём этапе; `max_per_session` для повторяемых |
| `cycles` | потолок каждого цикла с `reason` «выход к человеку» |
| `output` | обязательные строки финального ответа |

Каждая запись гарда покрыта тестом в `tests/rails/` (отказ, молчание, молчание для делегата). Схема — `.workflow/src/rails/README.md`.

## ⛔ Принцип изоляции скилов

Скилы НЕ знают о других скилах по имени. Используй: «любой скил проекта», generic ID (XXX-NNN).

**Изоляция от project-wide типов:** не хардкодить типы из `config.yaml:task_types`. Маршрутизация — по собственным типам скила, не по project-wide.

## Требования к качеству компонентов

| Компонент | Ключевые требования |
|-----------|--------------------|
| **Граф ядра** | один `E` на этап, порядок `E → R → S → G/Q`, лейблы ≥ 25 символов без `;`, checker зелёный |
| **Фрагменты** | узлы с глаголами, ссылки на knowledge/algorithms, гейт завершения с потолком |
| **Knowledge** | таблицы и списки, маркер `<!-- РАСШИРЕНИЕ -->`, формулы явно, источники; правил с ⛔/⚠️, отсутствующих в узлах, нет |
| **Algorithms** | вход → алгоритм → выход, пороги числами, пример применения |
| **Templates** | обязательные и опциональные поля, placeholder-подсказки, markdown |
| **tests/rails** | по тесту на гард, `node:test`, без запуска агентов |
| **README.md** | название, структура, flow по этапам, как расширять |

## Shared Knowledge — межскиловые знания

Модуль нужен 2+ скилам → выносится в `skills/shared/` (`shared/README.md` — обязательный индекс: таблица `| Модуль | Описание | Используется в |`, `shared/module.md` — сами модули).

| Правило | Описание |
|---------|----------|
| **Критерий выноса** | Контент используется 2+ скилами с пересечением 70%+ |
| **Скилы — универсальные, shared — проектный** | Скилы переносятся между проектами as-is. Shared содержит проектно-специфичные знания |
| **Ссылка из скила — через glob, одна каноническая строка** | В этапе 0 каждого скила — `S`-узел с модулем `.workflow/src/skills/shared/*` и условием: «**Перед началом работы** — если в проекте есть `.workflow/src/skills/shared/README.md`, прочитай этот индекс и загрузи модули, релевантные текущей задаче; отсутствие `shared/` — не блокер». Дословно эта формулировка (допустим только собственный триггер вместо «Перед началом работы»). Не хардкодить имена модулей и не перечислять примеры содержимого shared |
| **Path resolution — project-relative, не SKILL-relative** | Скилы подключены junction-цепочкой на canonical-каталог; путь через `..` от собственной location резолвится в canonical-каталог, где `shared/` нет. **Всегда project-relative путь**: `.workflow/src/skills/shared/<file>` от корня проекта |
| **Domain-контекст — в скиле** | Специфичная интерпретация shared-знаний остаётся в knowledge и узлах скила |

**Антипаттерны:** дублировать данные в knowledge/ нескольких скилов (вынести в shared/); хардкодить `.workflow/src/skills/shared/module.md` в узле (используй `.workflow/src/skills/shared/*` → проверить README); класть в shared/ knowledge одного скила; вкладывать shared/ в конкретный скил (shared/ — на одном уровне со скилами).
