# Алгоритм: Перевод скила на рельсы (проза → граф)

## Вход

- Директория скила `.workflow/src/skills/<name>/` в прозаической форме (SKILL.md с секциями, `workflows/*.md` с нумерованными шагами).
- Базовая версия для сверки покрытия: git-ref (обычно `HEAD` до начала правок).
- Инциденты скила: `coach-backlog.yaml` (analyzed_tickets, audited_skills), `tests/cases/*.yaml` → `origin.incidents`, `git log -- .workflow/src/skills/<name>/`.

## Алгоритм

### 1. Инвентаризация

1. `wc -l` всех файлов скила; список `workflows/`, `knowledge/`, `algorithms/`, `templates/`.
2. Тесты скила: L0-anchors (`tests/cases/*.yaml` → `assertions.static`), L2-рубрики (`tests/rubrics/`). Они обязаны остаться зелёными или быть перепривязаны в той же правке.
3. Фразы-инварианты: `node .workflow/src/scripts/check-rails-coverage.js --skill <name> --baseline <ref>` — печатает список предложений из строк с `⛔`, `⚠️`, жирным, датами, строк таблиц маршрутизации и загрузки.

### 2. Матрица переноса

Для каждой фразы-инварианта — ровно одна судьба:

| Судьба | Критерий | Куда |
|--------|----------|------|
| **Узел графа** | агент обязан цитировать это, стоя на этапе: правило, шаг, самопроверка, развилка, триггер загрузки | лейбл `R`/`S`/`G`/`Q` в ядре или фрагменте |
| **Справочник** | читается по надобности, не цитируется: обоснования, примеры, таблицы порогов, чеклисты по типам файлов, шаблоны | `knowledge/`, `algorithms/`, `templates/`; в графе — узел-триггер «загрузи …» |
| **Отказ** | фраза дублирует другой узел, устарела или противоречит концепции | запись `dropped: <обоснование>` в `rails-migration.yaml` |

Правило деления — **по цитируемости, не по размеру**. Длинный, но обязательный к цитированию текст остаётся в лейбле. Карта хранится в `rails-migration.yaml` рядом с `SKILL.md`:

```yaml
version: 1
skill: example-skill
baseline: <git-ref>
entries:
  - phrase: "подстрока фразы-инварианта ≥ 25 символов"
    target: "P4S2"                      # узел, файл или dropped: <обоснование>
```

### 3. Раздача этапов

1. **Ядро (`SKILL.md`, этапы 0–9)** — по существу скила: вход и правила роли (0), сбор данных (1), основная работа (2–4), самопроверка (5), отчёт и остановка (последний). Один `E` на этап, порядок `E → R → S → G/Q`.
2. **Ветки (`workflows/<type>.md`, этапы 10, 20, 30, …)** — по одному фрагменту на прежний воркфлоу; каждый шаг воркфлоу — `S`-узел; развилка «тип улучшения» — `Q`; выход ветки — ребро в узел ядра.
3. **Маршрутизация** — `Q`-узел в этапе 0 с рёбрами на `E` каждой ветки; метка ребра = тип работы; триггеры типов — в лейбле `Q`.
4. **Гейт перед каждым необратимым действием.** Критерий необратимости задаёт человек: пуш, удаление, установка зависимостей, запись в чужие артефакты, всё видимое снаружи. Не «выглядит страшно» и не мнение модели.
5. **Потолок у каждого цикла** — `G`, возвращающий назад, получает запись в `cycles` (`from == to` — возврат внутри этапа); повторяемые действия — `max_per_session`.
6. **Узлы вопроса стейкхолдеру** — шаги, где агент ждёт ответа, перечисляются в `pause_nodes`; терминальный узел — в `terminal`.
7. **Триггеры загрузки** — каждый файл `knowledge/`, `algorithms/`, `templates/` упоминается хотя бы одним узлом с условием загрузки; каноническая строка shared (`knowledge/skill-anatomy.md` → «Shared Knowledge») — отдельный `S`-узел этапа 0, дословно.

### 4. Гарды — только по инцидентам

Для каждого правила скила ответь: **видно ли нарушение в аргументах вызова инструмента или в тексте ответа?**

| Видно | Есть инцидент с датой | Решение |
|-------|-----------------------|---------|
| да | да | гард в `rails.yaml` (`write_scope`, `deny_shell`, `deny_mcp`, `stage_actions`, `cycles`, `output`) + дата и цена в лейбле узла + тест в `tests/rails/` |
| да | нет | остаётся текстом узла; гард появится после первого инцидента |
| нет | любое | остаётся текстом узла — честная граница, не недоработка |

Гард без теста не пишется. Тест: отказ там, где ждём отказ, молчание там, где ждём молчание, молчание для делегата.

### 5. Запись и проверка

1. Запиши `SKILL.md` (frontmatter + `rails: rails.yaml` + граф ядра), фрагменты, `rails.yaml`, `tests/rails/`, `rails-migration.yaml`. Перед записью каждого файла — чеклист универсальности (SKILL.md коуча, узел П3S1) и изоляция. Лейблы только в двойных кавычках: внутри кавычек mermaid 12.0.0 штатно разбирает `;`, бэктики и переносы строк (проверено 2026-09-22 настоящим парсером), `;` вне кавычек ломает схему; checker выдаёт на `;` предупреждение — заменяй, кроме канонической строки shared (она дословна).
2. `node .workflow/src/scripts/check-rails-graph.js --skill <name>` — ноль ошибок.
3. `node .workflow/src/scripts/check-rails-coverage.js --skill <name> --baseline <ref> --map rails-migration.yaml` — ноль пропусков.
4. L0-anchors и L2-рубрики скила зелёные (`run-skill-tests.js --skill <name>`); анchor на файл, которого больше нет, перепривязывается к узлу в той же правке.
5. Бюджет: ядро ≤ 400 строк; ядро + любой один фрагмент + его справочники ≤ 800.

## Выход

- Скил в графовой форме: `SKILL.md`, `workflows/*.md`, `rails.yaml`, `tests/rails/`, `rails-migration.yaml`.
- Отчёт: число узлов по типам, рёбер, этапов; число фраз-инвариантов и их судьбы (узел / справочник / отказ); список гардов с инцидентами; результат checker и coverage; L0/L2 статус.

## Пример

Прозаическое правило `**⛔ Коуч не выполняет git-операции:** git commit, git add … ни при каких условиях. Коммит делает исключительно пользователь.`

1. Цитируемость — да (агент обязан знать это, стоя на любом этапе) → узел `P0R4["П0 ПРАВИЛО: Коуч не выполняет git-операции … Коммит делает исключительно пользователь. Гард H2 …"]`.
2. Видно в аргументах — да (`Bash` с `git commit`), инцидент — правило с ⛔ существовало до рельс → гард `deny_shell` с `pattern: "\\bgit\\s+(commit|add|push|…)\\b"`, `incident: "SKILL.md P0R4"`.
3. Тест `tests/rails/git-deny.test.mjs`: `Bash("git commit -m x")` → deny; `Bash("git log")` → allow; тот же вход с `WORKFLOW_RAILS_ROLE=executor` → allow.
4. `rails-migration.yaml`: `phrase: "Коуч не выполняет git-операции"`, `target: "P0R4"`.
