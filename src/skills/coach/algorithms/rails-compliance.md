# Алгоритм: Оценка соответствия скила концепции рельс

## Вход

- Директория скила `.workflow/src/skills/<name>/`.
- Для поведенческой части: `node .workflow/src/rails/cli.mjs report --days <N> --skill <name>` (журнал `.workflow/logs/rails-denials.jsonl`), логи пайплайна `.workflow/logs/pipeline_*.log` за период, состояния сессий `.workflow/state/rails/*.json` (если сохранились).

## Алгоритм

### 1. Структурные метрики (статика) — при AUDIT, REVIEW, ANALYZE, CONVERT

Каждая проверка — детерминированная, по файлам. Итог — до 60 баллов.

| # | Проверка | Как измерить | Баллы |
|---|----------|--------------|-------|
| S1 | Граф валиден | `check-rails-graph.js --skill <name>` — 0 ошибок | 10 |
| S2 | `rails.yaml` есть и валиден | тот же checker, секция конфига | 5 |
| S3 | Правила живут узлами, не прозой | доля фраз-инвариантов (по `check-rails-coverage.js --baseline HEAD`) в лейблах узлов или справочниках, без прозы рядом с графом, дублирующей узлы: 100 % — 10, ≥ 90 % — 6, иначе 0 | 10 |
| S4 | У каждого гарда — тест | каждая запись `deny_shell`, `deny_mcp`, `stage_actions`, `cycles`, `output` упомянута хотя бы одним тестом в `tests/rails/` (grep по ключу или паттерну) | 10 |
| S5 | У каждого гарда — дата и цена инцидента | поле `incident` заполнено и узел-источник содержит дату `\d{4}-\d{2}-\d{2}` или `\d{2}\.\d{2}\.\d{4}` | 5 |
| S6 | У каждого цикла — потолок | для каждого `G`/`Q` с ребром назад есть запись в `cycles`; повторяемые действия имеют `max_per_session` | 5 |
| S7 | Гейт перед необратимым | каждое действие из `stage_actions`, помеченное необратимым (запись вне временных путей, прогон, коммит), предварено `G`-узлом в том же этапе | 5 |
| S8 | Ленивое — по цитируемости | ядро ≤ 400 строк; ядро + любой фрагмент + его справочники ≤ 800; ни один справочник не содержит правил с ⛔/⚠️, отсутствующих в узлах | 5 |
| S9 | Триггеры загрузки | каждый файл `knowledge/`, `algorithms/`, `templates/` упомянут узлом с условием; каноническая строка shared дословна | 5 |

**Скил без S1 и S2 (нет графа или `rails.yaml`) — CRITICAL «не на рельсах», остальные структурные баллы не считаются, рекомендация — CONVERT.**

### 2. Поведенческие метрики (динамика) — при ANALYZE

Источник — `rails report` и логи за период. Итог — до 40 баллов.

| # | Метрика | Как измерить | Интерпретация | Баллы |
|---|---------|--------------|---------------|-------|
| B1 | Отказы по узлу | `denials[node]` за период, отсортировать по убыванию | узел с ≥ 3 отказами в одной сессии — **дефект формулировки узла** (принцип 12), finding с рекомендацией переформулировать, не ужесточать | 10: нет таких узлов; 5: один; 0: два и более |
| B2 | Потолки | число срабатываний `cycles`/`max_per_session` | каждое — сессия, дошедшая до человека; ≥ 2 на один цикл за период — проверить формулировку гейта | 5 / 2 / 0 |
| B3 | Сбросы состояния | события `reset` | сброс без последующего `start` того же скила — ошибочный этап запер сессию: уточнить рёбра | 5 / 2 / 0 |
| B4 | Отказы выходного слоя | `stop_blocks`, повторы раннера по output-check | ≥ 2 за сессию — требования `final_requires` или узел отчёта сформулированы неясно | 5 / 2 / 0 |
| B5 | Переходы без маркера | действия этапа, отклонённые из-за E-узла или отсутствия состояния | агент действует, не объявив узел: усилить `E`-лейбл или триггер ветки | 5 / 2 / 0 |
| B6 | Завершённость сессий | доля сессий, дошедших до `terminal`, среди начатых | < 70 % — искать узел обрыва (последний `node` в состоянии) | 10: ≥ 90 %; 5: ≥ 70 %; 0 |

### 3. Findings

Каждая проверка с потерей баллов — finding с полем «принцип концепции №» (`knowledge/rails-concept.md`), файлом или узлом, evidence (строка журнала, вывод checker'а, `file:line`) и рекомендацией. Для B1 рекомендация всегда «переформулировать узел `<id>`: <что именно непонятно по тексту отказов>», для остальных — по таблице.

## Выход

| Балл (S + B) | Оценка | Действие |
|--------------|--------|----------|
| 90–100 | **ON_RAILS** | штатно; читать журнал раз в период |
| 70–89 | **DRIFT** | правка узлов по findings, тест |
| 40–69 | **WEAK** | правка узлов и гардов, добавить недостающие тесты гардов |
| < 40 или нет графа | **OFF_RAILS** | CONVERT |

Секция «Соответствие концепции» в отчёте аудита и анализа: балл, оценка, нарушенные принципы, узлы-спотыкачи (B1) с числом отказов.

## Пример

`example-skill`: S1 10, S2 5, S3 6 (три фразы-инварианта в README без узлов), S4 5 (гард `run_tests` без теста), S5 5, S6 0 (гейт П4 без потолка), S7 5, S8 5, S9 5 = 46; B1 5 (узел P3S1 — 4 отказа в одной сессии), B2 5, B3 5, B4 2, B5 5, B6 10 = 32. Итого **78 — DRIFT**: findings — принцип 1 (README), принцип 15 (тест гарда), принцип 10 (потолок), принцип 12 (переформулировать P3S1: в отказах повторяется «не понял, что считать закрытым списком»).
