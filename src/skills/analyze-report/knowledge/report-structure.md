# Структура отчётов и извлечение данных

Описание типовой структуры отчётов workflow-ai и правила извлечения данных из них.

## Типовая структура отчёта

Отчёты находятся в `.workflow/reports/` и содержат:

| Секция | Что извлекать | Как искать |
|--------|--------------|-----------|
| **Frontmatter** | ID, дата, связанный план, период | По ключам frontmatter |
| **Результат/выполненные задачи** | Список завершённых тикетов, результаты | Секция с перечнем сделанного — заголовок варьируется по проекту («Выполненные задачи», «Результат выполнения», «Сводка» и т.п.), ищи по содержимому, а не по точному заголовку |
| **Проблемы/риски** | Заблокированные задачи, ошибки, отклонения | Секция с описанием блокеров/рисков/аномалий (заголовок варьируется) |
| **Статистика** | Количественные данные: done/total, время | Секция с числовыми показателями (заголовок варьируется) |
| **Рекомендации** | Выводы предыдущего анализа (если есть) | Секция с рекомендациями/предложениями |

## Извлечение данных из тикетов

### Из завершённых тикетов (done/, archive/, review/)

| Поле | Где искать | Зачем |
|------|-----------|-------|
| `id` | Frontmatter | Идентификация |
| `complexity` | Frontmatter | Weighted completion |
| `created_at` / `completed_at` | Frontmatter | Время выполнения |
| **Result** | Секция результата выполнения (заголовок варьируется — см. «Типовая структура отчёта» выше) | Что реально сделано и какие расхождения записаны |
| **Найденные дефекты** | Подраздел `### Найденные дефекты` секции результата (поле recorded_defects скрипта), у тикета без подраздела (defects_section_missing) — секция результата целиком и заметки | Записанный дефект без более позднего исправления — пробел в `gaps` (узел P10S13), а не рекомендация стейкхолдеру: зелёная запись проверки тикета тестирования подтверждает только, что сценарий проведён. В рекомендации он идёт, только если его исправление исключает раздел плана «Исключено из scope» или стейкхолдер записал решение по нему; запись только об отсутствии дефектов — не находка |
| **DoD** | Секция критериев | Все ли выполнены |
| **Ревью** | Секция `## Ревью`: строки таблицы с вердиктом passed, failed или skipped | Прошёл ли с первого раза (первая строка с passed или failed) и сколько возвратов (строки ❌) — поля first_pass_rate, rework_rate и reworked_tickets скрипта, не пересчитывать |

### Из заблокированных тикетов (blocked/)

| Поле | Зачем |
|------|-------|
| `id`, `title` | Идентификация |
| `dependencies` | Что блокирует |
| Причина блокировки | Для описания пробела в `gaps` (узел P6R4): тикет в blocked/ — has_gaps, не рекомендация стейкхолдеру |
| Пункт DoD с его записью и его выводом из evidence ревью (`.workflow/state/evidence/<имя файла тикета>.json`) | Для пробела о записи проверки тикета тестирования (узел P6R5): держит тикет запись или дефект продукта |

### Из тикетов в работе (in-progress/)

| Поле | Зачем |
|------|-------|
| `id`, `title` | Текущая работа |
| `created_at` | Как давно в работе |

## Извлечение данных из планов

| Секция плана | Что извлекать |
|-------------|--------------|
| **Цели** | Ожидаемые результаты для сравнения |
| **Задачи** | Полный список для подсчёта покрытия |
| **Приоритеты** | Для оценки порядка выполнения |
| **Риски** | Для проверки — сработали ли |

## Правила работы с данными

- **Считай только то, что есть** — не экстраполируй, не предполагай
- **Указывай источник** — для каждой метрики укажи откуда взяты данные
- **Отмечай пробелы** — если данных не хватает для вывода, явно укажи
- **Разделяй факты и выводы** — сначала данные, потом интерпретация
