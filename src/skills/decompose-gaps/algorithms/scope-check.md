# Алгоритм: Проверка scope gap

Формализованный алгоритм определения, входит ли gap в scope декомпозиции.

## Вход

| Параметр | Тип | Описание |
|----------|-----|----------|
| `gap` | string | Описание одного конкретного пробела |
| `report` | file | Содержимое отчёта REPORT-{id}.md |
| `plan` | file | Содержимое исходного плана PLAN-{id}.md |

## Выход

| Параметр | Тип | Описание |
|----------|-----|----------|
| `in_scope` | boolean | true — создавать тикет, false — записать в «Новые требования» |
| `reason` | string | Обоснование решения |
| `check_failed` | string | Номер проверки, на которой gap был отклонён (если отклонён) |

## Алгоритм

```
FUNCTION check_scope(gap, report, plan) → {in_scope, reason, check_failed}

  # Шаг 1: Проверка источника
  source_section = найти секцию отчёта, откуда извлечён gap

  IF source_section описывает рекомендации, планы на будущее или гипотезы (не выполненную/заблокированную работу текущего прогона):
    RETURN {false, "Gap из секции '{source_section}' — не является пробелом", "1"}

  IF source_section не определяется по тексту gap:
    source_section = "Выполненные задачи"  # fallback — переходим к шагу 2

  IF source_section не описывает выполненную или заблокированную работу текущего прогона:
    RETURN {false, "Gap из неизвестной секции '{source_section}'", "1"}

  # Шаг 2: Проверка принадлежности к плану
  matching_task = найти задачу в plan, которой соответствует gap
  # Секция «Критерии успеха» плана определяет, что план выполнен: gap о её пункте, который
  # записанные данные опровергают или не подтверждают, принадлежит плану и без отдельной
  # задачи. Снимает только шаг 2 «нет задачи», шаг 3 «все ключевые задачи выполнены» и
  # техдолг шага 5; шаг 2a и расширение scope к нему применяются.
  criterion_gap = gap описывает пункт «Критерии успеха» plan, который записанные данные опровергают или не подтверждают

  IF matching_task == NULL AND NOT criterion_gap:
    RETURN {false, "Нет соответствующей задачи в исходном плане", "2"}

  # Шаг 2a: Проверка exclusions из scope плана
  plan_exclusions = извлечь секцию «Исключено из scope» / «Excluded from scope» из plan

  IF plan_exclusions != NULL:
    FOR EACH exclusion IN plan_exclusions:
      IF gap описывает работу, подпадающую под exclusion:
        RETURN {false, "Gap подпадает под исключение из scope плана: '{exclusion}'", "2a"}

  IF gap описывает расширение scope (новый функционал, не заявленный в плане):
    RETURN {false, "Расширение scope за рамки плана", "2"}

  # Шаг 2b: Заблокированный тикет тестирования (узлы P10R1, P10R2, P0R7). Тикет в blocked/ не
  # закрыт и сам не сдвинется: ни «deliverable другого тикета», ни «все ключевые задачи
  # выполнены», ни workflow-управление, ни организационный gap (шаги 2–5) к нему не относятся — новый тикет с
  # `unblocks` или `supersedes` его не двигает, поля — данные для пайплайна. Что создать —
  # граничные случаи ниже, а не «Новые требования».
  # Тикет тестирования в blocked/ держит его собственная запись проверки (узлы P10R4, P10R5):
  # по blocked_reason и evidence ревью — отказ гейта в записи пункта, пункт со статусом
  # timeout или denied или с причиной dod_record_invalid, ожидание по тексту вывода, которое
  # не совпало. Не совпало ожидание по коду выхода — дефект продукта: без пункта с признаком —
  # следующий IF. Вывод пункта с признаком показывает невыполненный критерий — ещё и дефект
  # продукта (узел P10R5). Новый тикет-замена с переписанной записью заблокированный тикет не
  # правит.
  IF gap описывает тикет тестирования в blocked/, которого держит его собственная запись проверки:
    RETURN {true, "Запись заблокированного тикета тестирования — узел P10R4", NULL}

  IF gap описывает тикет тестирования в blocked/ за записанным им дефектом плана:
    RETURN {true, "Заблокированный тикет тестирования — узел P10R2", NULL}

  # Другой тикет закрывает gap, только если его результат записан после события,
  # от которого gap возник (узел P10R1): тикет тестирования, записавший дефект до
  # исправления, повторную проверку после исправления не закрывает.
  IF gap — deliverable другого тикета (создан как часть DoD) AND результат того тикета записан после события, от которого возник gap:
    RETURN {false, "Deliverable другого тикета, не gap", "2"}

  # Шаг 3: Проверка статуса плана
  plan_status = извлечь status из plan

  IF plan_status == "completed":
    RETURN {false, "План завершён — gaps = новые инициативы", "3"}

  # Опровергнутый или неподтверждённый пункт «Критерии успеха» значит, что план не
  # выполнен, даже если все его тикеты в done/.
  IF все ключевые задачи плана выполнены AND NOT criterion_gap:
    RETURN {false, "Все ключевые задачи выполнены", "3"}

  # Шаг 4: Проверка workflow-управления (заблокированный тикет тестирования принят на шаге 2b)
  IF gap содержит действия:
    - перемещение тикетов
    - изменение статуса других тикетов
    - запуск workflow-скриптов
    - операции с .workflow/tickets/, .workflow/plans/, .workflow/reports/
  :
    RETURN {false, "Содержит инструкции по workflow-управлению", "4"}

  # Шаг 5: Проверка организационных/процессных gaps
  IF gap описывает:
    - утверждение/активацию плана человеком
    - инвентаризацию накопленных багов/техдолга прошлых итераций (кроме criterion_gap: падения, опровергающие пункт «Критерии успеха» плана, — пробел плана, даже если записаны как прежние)
    - работу с планом, отличным от плана текущего прогона (особенно draft)
    - процессное улучшение пайплайна/скилов, обнаруженное попутно
  :
    RETURN {false, "Организационный/процессный gap — вне скоупа прогона", "5"}

  # Все проверки пройдены
  RETURN {true, "Gap в scope: соответствует задаче '{matching_task}' плана", NULL}
```

## Пример применения

**Вход:**
- gap: "Не реализована валидация входных данных в модуле обработки"
- report: REPORT-{id} (секция «Выполненные задачи», статус задачи: partial)
- plan: PLAN-{id} (задача #3: "Реализовать валидацию входных данных", status: in_progress)

**Прохождение:**
1. Источник: «Выполненные задачи» → ✅ валидный источник
2. Принадлежность: задача #3 плана → ✅ есть в плане
3. Статус: plan status = in_progress → ✅ план не завершён
4. Workflow: нет управляющих инструкций → ✅
5. Организационный/процессный: нет → ✅

**Выход:** `{true, "Gap в scope: соответствует задаче #3 плана", NULL}`

## Граничные случаи

Тикет тестирования в blocked/, которого держит его собственная запись проверки, решает строка о записи проверки, даже если подходит и строка выше о тикете тестирования в blocked/ (узел P10R4).

| Случай | Решение |
|--------|---------|
| Gap на стыке двух задач плана | Создать один тикет, ссылаясь на обе задачи |
| Gap частично в scope, частично нет | Разделить: in-scope часть → тикет, out-of-scope → «Новые требования» |
| Заблокированная задача по внешней зависимости | Не gap — внешние зависимости не контролируются скилом |
| Gap описывает «улучшить» вместо «исправить» | Проверить, было ли в DoD плана — если нет, out of scope |
| Дефект из тестирования исправлен другим тикетом, сценарий после исправления не перепроверен, тикет тестирования закрыт | В scope: исправление с фразой «Исправление дефекта {ID тикета тестирования}» в заголовке или описании и тикет повторной проверки, зависящий от исправления (узлы P10R1, P10R2) — существующий тикет исправления скил не правит; по этой фразе закрытие плана признаёт записанный дефект исправленным |
| Каждый дефект, записанный тикетом тестирования, исправлен другим, уже готовым тикетом, тикет тестирования в blocked/ | В scope: тикет повторной проверки, зависящий от исправления, с `supersedes: [ID тикета тестирования]` — пайплайн закроет заменённый, когда проверка будет готова (узел P10R2) |
| То же, но сценарий после исправлений уже перепроверил другой готовый тикет без `supersedes` | В scope: всё равно новый тикет повторной проверки с `supersedes: [ID тикета тестирования]` — существующий скил не правит, а без поля пайплайн заблокированный не закроет (узлы P10R1, P10R2) |
| Дефект из тестирования, исправления ещё нет, тикет тестирования в blocked/ | В scope: один тикет исправления с `unblocks: [ID тикета тестирования]`, второго тикета проверки нет; другие дефекты того же тикета уже исправлены — для них тоже без `supersedes`: тикет тестирования после исправления перепроверит все дефекты сам (узел P10R2) |
| Тикет тестирования в blocked/ уже назван в `unblocks` открытого тикета исправления (backlog/, ready/, in-progress/, review/) | В scope, новый тикет не нужен: пайплайн вернёт тикет тестирования, когда исправление будет готово (узел P10R2); держит его собственная запись проверки — строка о записи проверки ниже (узел P10R4) |
| Исправление, которое называет тикет тестирования в `unblocks`, само в blocked/ | В scope: замена исправления с `unblocks: [ID тикета тестирования]` и `supersedes: [ID заблокированного исправления]`; заблокированное скил не правит, новая проверка с `supersedes` на тикет тестирования его не снимет (узел P10R2) |
| Тикет тестирования в blocked/ уже назван в `supersedes` повторной проверки, которая сама не готова (blocked/ или открыта) | В scope, новый тикет для него не нужен: решение — по gap этой проверки как тикета тестирования (узел P10R2), пайплайн закроет тикет тестирования цепочкой |
| Тикет тестирования в blocked/, исправления нет, план исключает исправление найденных дефектов | Вне scope (шаг 2a — раньше шага 2b): исправление не создаётся, gap — в «Новые требования»; исправления всех дефектов уже готовы — повторная проверка с `supersedes` в scope, исключённой работой она не является (узел P10R2) |
| Тикет тестирования в blocked/ держит его собственная запись проверки (по blocked_reason и evidence ревью: отказ гейта в записи пункта, пункт со статусом timeout или denied или с причиной dod_record_invalid, ожидание по тексту вывода, которое не совпало) | В scope (шаг 2b): повторная проверка с `supersedes` по узлу P10R5, зависящая от каждого исправления его дефектов и провалов его вывода, а если он уже назван в `supersedes` незавершённой проверки — работа по ней; новые исправления без `unblocks` на него; заблокированный тикет не правится, это не workflow-управление (узел P10R4). План исключает исправление дефектов — исправлений нет, запись пункта с провалами переписывается, провалы — в «Новые требования», повторная проверка в scope |
| Не совпало ожидание по коду выхода, исполнитель назвал провалы посторонними, прежними или не связанными с тикетом | Не запись проверки, а дефект продукта, найденный тикетом тестирования: без пункта с признаком записи — ветки узла P10R2, с ним — узел P10R4, провалы получают исправления (узел P10R5) |
| Все тикеты плана в done/, пункт «Критерии успеха» плана опровергнут самым поздним записанным результатом (прогон проверок с падениями) или не подтверждён ни одним тикетом и отчётом | В scope (criterion_gap: шаги 2, 3 и техдолг шага 5 его не отклоняют; шаг 2a и расширение scope в силе): опровергнут — тикет исправления, DoD которого — проверка этого пункта; не подтверждён — тикет проверки этого пункта. Исполнитель назвал падения посторонними или прежними — всё равно в scope: пункт плана требует их отсутствия |
