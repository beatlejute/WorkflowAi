## [1.24.0] — 2026-10-02

### Added
- **Запрет «модель недоступна».** Три запуска подряд со сбоем, не прошедшие контроль артефактов (`error`, `timeout`), выводят модель из выбора исполнителя на час; каждая следующая неудача без успеха удваивает срок, потолок — сутки; серия обнуляется успешным запуском, `unban_model` без типа тикета и событием `reset`. Ограничение провайдера (`throttled`, 429 и квота) и сетевой сбой (`network_error`) серию не удлиняют и не прерывают: ночной сбой прокси не должен выводить модели из строя на сутки. В запрет кладутся последние 10 доказательств, полная длина серии — в `failures`. PulseProxy 2026-09-29…30: qwen3.8-27b, gemini-3.5-flash-lite, nemotron-3-super и nemotron-3.5-lightning выбирались повторно после исчерпанной квоты — на них ушло около пяти часов.
- **Машинная метка начала работы `started_at`.** Ставится кодом при первом входе тикета в `in-progress/` — на всех путях (`move-ticket.js`, `moveTicket` из operations, через него MCP `move_ticket` и `resolve_human_ticket`, авто-коррекция `pick-next-task.js`). Повторный вход метку не сдвигает, уход из колонки не стирает, пустое или выдуманное значение заменяется. Метка — база проверки `file_unchanged` в `verify-artifacts.js`: раньше базой служил `created_at`, который агент декомпозиции писал полуночью, и работа, сделанная до неё, объявлялась «не изменённой» (PulseProxy PLAN-020: 7 ложных отказов, 73 минуты платных перезапусков, косметическая правка ради mtime). Метки нет — проверка пропускается, а не проваливается.
- **След обрыва раннера.** В лог прогона идут строки `RUNNER CRASH`, `RUNNER EXIT`, `RUNNER STOP`, `RUNNER ERROR` с кодом, сигналом, стадией и стеком, а открытый запуск агента закрывается как прерванный; пока агент работает, раз в 5 минут пишется `HEARTBEAT`. Раньше прогон, запущенный из MCP, отдавал stderr в `ignore`, и причина смерти не сохранялась нигде (PulseProxy 2026-09-30: прогон умер, лог молчал).
- **`changed_paths` у сбойного запуска.** Запуск со статусом `error`, `timeout` или `network_error`, оставивший правки, пишет их пути (до 30, полное число — в `changed_files`) в событие журнала и в колонку «Изменённые файлы» строки «Истории работы»: следующая попытка видит точный список вместо вывода из общего дерева.
- **Стадии уровня плана — `scope: plan`.** `create-report`, `analyze-report`, `decompose-gaps` и `complete-plan` получают контекст без ключей тикета; пустой `plan_id` берётся из `related_plan` отчёта. Раньше стадии получали чужие `ticket_id` и `task_type`, а история работы дописывалась в закрытые тикеты.
- **`check-report-needed`: статус `stuck`.** Тикет плана в `blocked/`, из-за которого доска не меняется, больше не выглядит как «изменений нет»: стадия отдаёт `stuck` с ID и причиной блокировки, пайплайн завершается строкой «Pipeline stopped: plan … is stuck» (ключ `stuck: end` в конфиге). До этого застрявший тикет крутил отчёт → разбор → разбиение без результата.

### Changed
- **План закрывает только стадия закрытия.** `pick-next-task` больше не пишет плану `completed` по счёту тикетов: он сообщает в логе «all N tickets done — closing is up to complete-plan». `complete-plan` идемпотентен и отвечает `not_ready` с перечнем открытых тикетов (`blocked_tickets` и `[WARN] ID: blocked — причина`) и с записанными в тикетах дефектами без исправления (`defects`). PulseProxy 2026-09-30: план закрылся в 17:33, за девять секунд до старта отчёта и за пять минут до разбора — гейт критериев успеха был обойдён.
- **Записанный дефект не даёт закрыть план, пока не исправлен** (`lib/utils.mjs`, `complete-plan.js`, `calc-plan-metrics.js`, `calc-metrics.js`). Дефект — подраздел «### Найденные дефекты» результата тикета (`нет` и равнозначные записи дефектом не считаются, блоки кода не обрывают разбор). Исправлением признаётся более поздний готовый тикет того же плана с `unblocks` или `supersedes` на записавший тикет либо с фразой «Исправление дефекта ID» в заголовке или описании; тикет, закрытый заменой, исправлен своей заменой. PulseProxy QA-175 записал дефект подсказки `geoBlockedTitle`, три разбора его пропустили, план закрылся с дефектом в коде.
- **Ревью видит изменения человека вне области** (`verify-artifacts.js`, `configs/pipeline.yaml`): тикет `executor_type: human` с правкой файлов проекта вне `context.files`, с масками `visual` и с путями после `--` уходит на ревью агентом (legacy, предупреждение `human_out_of_scope_changes`), а не закрывается скриптом без модели. Разбор «Изменённых файлов» переписан: HTML-комментарии шаблона вырезаются, берутся все пути строки, путь без обратных кавычек даёт предупреждение (RSH-002: закомментированный пример `path/to/file1.ts` провалил проверку артефактов и стоил повторного запуска opus).
- **Селектор модели стадии: повтор и старт по сложности.** Сбой вызова селектора повторяется один раз; если снова сбой, уровень берётся по `complexity` тикета (simple/medium/complex), а не самым низким. Раньше `R: lowest` отправлял сложный QA-тикет на haiku первого уровня (PulseProxy QA-177 — исполнитель подделал отчёт).
- **Рельсы.** Канарейка `RAILS_CANARY` — событие `canary`, а не отказ: не растит счётчики узла и не зашумляет журнал (в двух проектах она составляла 24–28% записей). Цитата лейбла обрезается по границе фразы, строка отказа показывает ту же цитату, что в команде перехода. Отказ «похожа на запись» называет токен, из-за которого команда признана записью, и больше не отклоняет законные чтения, прогон базовых тестов и чистку временных файлов. Отказ `write_scope` называет фактическую цель и корень проекта. `check-rails-graph` предупреждает о цепочке длиннее трёх узлов-правил подряд. `rails goto` в терминальный узел печатает литералы `final_requires`, `rails status` печатает «Переходы» так же, как `goto`, `rails report` печатает канарейку отдельной строкой.
- **Промпт стадии называет файлы скила**: второй строкой — `.workflow/src/skills/<skill>/` и `SKILL.md`. Агенты не находили относительный путь справочника и шли по графу вслепую (в PulseProxy SKILL.md читали 4 сессии из 16).
- **Шаблоны пакета.** Тикет: секция результата приведена к одному набору подсекций («Что сделано», «Изменённые файлы», «Найденные дефекты», «Заметки»), «Время выполнения» с `Started`/`Completed`/`Agent used` удалено (время и агента пишет пайплайн), пример пути в «Изменённых файлах» больше не строка-буллет, поля времени помечены «ставит скрипт пайплайна, не заполнять», в комментарии записей проверки — поиск по пути, который игнорирует git (`--no-exclude-standard`) и оговорка «check не зависит от чужой работы, кроме тикетов-зависимостей». План: поле `end_date` (по нему считается здоровье плана), секция «Справочные данные» (без неё шаблон не проходил валидатор полноты), комментарии к задачам, рискам, внешним зависимостям и критериям успеха.
- **Настройки рельс трёх скилов.** `create-report` — потолок возврата от гейта полноты «Проблем»; `create-plan` — узел паузы `P6S3` для вопросов стейкхолдеру (ответ там требует строку `RAILS: P6S3`, статус `approved` запрещён); `decompose-plan` — запуск `verify-atomicity.js --activate` из скила отклоняется (план активирует только стадия).
- **Скилы: анализ двух прогонов.** Прогоны PulseProxy PLAN-020 и ListeningGlass PLAN-001 разобраны по 62 тикетам, логам, отчётам и журналам отказов: 124 находки, 53 темы, каждая проверена отдельно. Правки внесены в девять скилов; перечислены ниже в разделе «Fixed».

### Fixed

PulseProxy PLAN-020: 8 из 9 отказов модели ревью — на пункте «проверяет задача N», около 127 минут и 10 платных запусков; ListeningGlass: причина сбоя service worker названа по догадке четыре раза по-разному.
- **`analyze-report`: дефекты, записанные выполненными тикетами, доходят до `gaps`** (узел P10S13, исключение в P6R2, условие в P6Q1): подраздел «Найденные дефекты» читается у каждого выполненного тикета плана, записанное расхождение без более позднего исправления — пробел, а не рекомендация стейкхолдеру; решение плана «исправление исключено» и перенос дефекта стейкхолдером остаются в силе. Метрики возвратов считаются по таблице «Ревью» (First-Pass Rate и Rework давал скрипт `calc-plan-metrics.js`, а не агент вручную: по одному плану выходило 63,64% → 100% → 100% при фактических 66,7%).

Отчёты писали «проблем нет» при 23 строках ❌ у 12 тикетов.
- **`create-plan`**: поведение, которое доказывают тесты парной задачи, — критерий парной задачи (отсылка «проверяет задача N» в причине `prose` — ошибка валидатора); у задач, которые пишут тесты или проводят сценарий, — строка критерия о покрытии случаев и измеренных значениях (счётчик с порогом без альтернативы, снимающей порог); критерий о наборе доказывается каждым объектом; митигация риска, зависящая от ответа спайка, — критерий задачи-получателя с зависимостью; критерий успеха закрывается задачей плана, внешнее событие — во «Внешних зависимостях»; модель видит картинку, но не размер и формат файла — это `check`; артефакт во внешнем каталоге — задача публикации; правка утверждённого плана описана в жизненном цикле.
- **`decompose-plan` и `decompose-gaps`**: поля времени тикетов не заполняет модель (ставит скрипт); ID нового тикета берётся скриптом выделения, а не вручную; при нуле пробелов в scope узлы создания тикета не проходятся; при разбиении задачи плана на несколько тикетов текст критерия переносится дословно, придуманный запрещён; запрет пункта DoD «Результаты внесены в файл тикета» у человеческих тикетов; поиск по `.workflow` — по точному пути, а не Glob от корня (каталог в `.gitignore`, у части агентов поиск слеп); сводный тикет проверки зависит от всех тикетов реализации; закрытый тикет тестирования заводит пару «Исправление дефекта ID» + повторная проверка — по этой фразе закрытие плана признаёт дефект исправленным.
- **`review-result`**: шкала уровней не засчитывает факт, написанный самим исполнителем, за доказательство; в шапке оговорено, что граф — процедура тикетов старого формата, тикеты `dod_format: 2` ревьюит стадия по evidence; база `file_unchanged` — `started_at`; разбор «Изменённых файлов» и человеческие тикеты вне области (см. «Changed»).
- **`coach`**: факты о работе исполнителя берутся из истории, лога и журнала запусков агентов, а не из самоописания; канарейка исключена из метрики отказов; правило слияния цепочек узлов-правил; требования к началу лейбла узла; литералы финального ответа — в терминальном узле (то же в `manual-testing`).
- **`check-ticket-dod.js`**: тикет `dod_format: 2`, включая `human`, получает `dod_record_invalid: пункт N (<ошибка>)` на ошибки формы записи (нет формы, две формы, `prose` без причины, `visual` без пути, ключи без `check`) — раньше проходил молча.
- **`move-to-ready.js`**: штампует поля времени по тому же правилу, что `verify-atomicity.js` (пустое, неразбираемое или будущее значение заменяется текущим временем, валидное прошлое не трогается) — тикеты, не прошедшие проверку атомарности, больше не остаются с пустой датой.
- **workflow-mcp**: `resolve_human_ticket` пишет результат в штатную секцию результата и отмечает только подтверждённые пункты DoD — при `review`/`done` с неотмеченными пунктами и без `dod_confirmed` отвечает `DOD_NOT_CONFIRMED` (смена контракта), решение в журнале режется по границе слова, а не посреди; stderr раннера пишется в файл `<run_id>.stderr` рядом с логом; в описаниях инструментов — правило «правку кода продукта из человеческого тикета выносить отдельным тикетом».

## [1.23.0] — 2026-09-30

Без флага скрипт только проверяет тикеты и отвечает `plan_status_reason: activation_not_requested`; флаг внутри текста промпта флагом не считается. - **Выбор модели стадии — поле `selection` (README «Выбор модели стадии», `src/lib/stage-selection.mjs`).** Стадия исполнителя с `selection` берёт не место курсора попытки, а самую слабую достаточную модель: кандидаты — выжившие фильтров курсора (способности, health-реестр, запреты, пробованные в попытке, `max_per_attempt` пула), пулы — участниками; уровни — полосы равной ширины между наименьшей и наибольшей оценкой `intelligence` выживших, их число — число текстов `selection.levels` (рубрика сложности тикета); нижняя граница тикета — наибольший уровень его запусков с градациями `refused`, `empty`, `artifacts_failed`, `review_failed` из журнала, не выше сильнейшего уровня минус 1; селектор `selection.selector` — не больше одного вызова на попытку, отвечает требуемым уровнем и ранжиром. Порядок обхода: бесплатные от требуемого уровня вверх, затем платные, затем слабее — от сильных. Отсеянные кандидаты селектору не показываются и не запускаются. Сбой, таймаут, ответ без уровня или пропуск селектора (`no_ticket`, `unhealthy`, `stopped`, `single_candidate`, `single_level`) — лестница от слабых. Ни у одного выжившего нет оценки (сбой команды фактов, каталог OpenRouter не загружен и кэша нет) — попытка идёт прежним курсором по местам с теми же фильтрами, селектор пропускается (`skipped:no_scores`), в журнале `selection: cursor`: иначе все были бы на уровне 1, граница не росла бы, и попытки пускали бы подряд одних участников пулов. `escalate_on: [blocked]` — агент сам ответил `blocked`: следующий строго сильнее уровнем в той же попытке, сильнее нет — `goto.blocked`. Сканер секретов покрыт тестами пути по умолчанию и относительного `--path`.
- **Тесты не завязаны на Windows и на форму временного каталога.** Прежде CI падал на всех трёх ОС, и публикация по метке версии не доходила до npm. Проверки, завязанные на Windows (замена занятого файла, путь `kilo.cmd`), идут только там или берут путь своей ОС; временные каталоги берутся в полной форме (`/var` → `/private/var` на macOS, `RUNNER~1` на Windows); проверка лестницы повторов считает попытки, а не миллисекунды.

### Added
- **Безынструментные агенты (`kind: http`).** Модель, которая не пользуется инструментами, подключается записью в `pipeline.agents`, без правок кода: `kind: http`, `protocol` (`chat` или `decisions`), `url` (`https://`; `http://` — только localhost, 127.0.0.1, ::1), `model`, `auth` (`{ env: <ИМЯ> }` или `{ kilo_oauth: true }`), `timeout_s` (на одну попытку). Протокол `chat` — формат OpenAI chat completions без `tools`, с изображениями (PNG, JPEG, WebP; до 5 МБ, до 8 на запрос); `decisions` — типизированная оценка OpenRouter. Общий клиент — `src/lib/model-client.mjs`: ключ только из переменной окружения или токена kilo (на Windows имя переменной — без учёта регистра), прокси из `HTTPS_PROXY` и соседних переменных (туннель CONNECT), до двух повторов на 429/500/502/503 и сетевую ошибку, прерывание через `AbortSignal`, классы ошибок `no_key`, `auth`, `rate_limit`, `server`, `timeout`, `network`, `bad_request`, `bad_response`, `aborted`.
- **Слой оценки** (`src/lib/model-evaluate.mjs`): вопросы с уровнями на входе, уровень 1..n по каждому вопросу на выходе — одинаково для обоих протоколов.
- **Обмен стадии с моделью (`model_io`).** Стадия с `model_io: { prepare, apply, options }` исполняется агентом `kind: http` в три шага: скрипт prepare собирает вопросы, раннер спрашивает модель через слой оценки и пишет ответ в `.workflow/state/model-io/<стадия>-<run_id>-<id вызова>.json`, скрипт apply выдаёт статус стадии. Ошибка модели — `status: error` с `error_class` (нарушение контракта prepare — `bad_prepare`), в истории работы тикета — `error`; остановка пайплайна снимает запрос к модели и не запускает apply (`aborted`); `auth`, `rate_limit`, `server`, `timeout`, `network` помечают агента в health-реестре и передают стадию следующему агенту. В лог пишется строка `MODEL_IO` с моделью, длительностью шагов и `cost_usd`. Модель стадии выбирается по `required_capabilities`: для изображений — агент с `multimodal`.
- **Защита от ошибочного назначения.** Проверка конфига при старте отклоняет агента `kind: http` в стадии без `model_io` (`agent`, `agents`, `agents_by_type`) и в `default_agents`/`default_agent`, а также неполную или противоречивую запись агента и `model_io` со ссылкой на несуществующий скрипт. Тесты скилов не берут такого агента исполнителем (`target_agents`, `--agent`); судьёй он допустим.
- **Причина ошибки в выводе тестов скилов.** `run-skill-tests.js` со `status: error` печатает строку `error: …`.

### Fixed
- **Остановка пайплайна передавала стадию следующему агенту.** Агент, убитый по SIGINT/SIGTERM, выглядел как обычный сбой: при пустом diff артефактов `executeWithFallback` запускал следующего агента списка уже после запроса на остановку, а убитый агент мог попасть в health-реестр. Теперь после остановки стадия завершается ошибкой убитого агента, без перехода к следующему и без пометки.

### New Features
- **New built-in stage type: `manual-gate`** — Adds support for manual approval steps in pipelines. When a stage with `type: manual-gate` is encountered, the runner creates a pending approval file in `.workflow/approvals/{step_id}.json` and enters a polling loop, waiting for an external decision (`approved`/`rejected`).

  **Key capabilities:**
  - Deterministic `step_id` generation: `{ticket_id}_{stageId}_{attempt}` (e.g., `QA-12_manual-approve_0`)
  - Idempotent file creation — pending file is not overwritten on retry/restart
  - Configurable polling interval (`poll_interval_ms`, default 2000ms) and optional timeout (`timeout_seconds`)
  - Graceful handling of SIGTERM/runner stop (returns `aborted`)
  - Immediate return if file already has `approved`/`rejected` status (crash recovery)
  - JSON approval file format with full audit trail (`created_at`, `updated_at`, `decided_by`, `comment`, `context_snapshot`)

  **Pipeline configuration example:**
  ```yaml
  stages:
    manual-approve-deploy:
      type: manual-gate
      poll_interval_ms: 2000
      timeout_seconds: 86400
      goto:
        approved: continue-deploy
        rejected: rollback
        timeout: notify-stuck
        aborted: end
  ```

  **Two approval methods (both opt-in):**
  1. **External MCP/client**: tools like `workflow-mcp` can write to approval files programmatically
  2. **Direct file edit**: users can simply edit `.workflow/approvals/{step_id}.json` and change `status` to `approved` or `rejected`

  **Important:** `manual-gate` is **opt-in** — pipelines without such stages work identically to previous versions. No breaking changes.
