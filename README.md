## Синглтон семантика Pipeline

Система workflow реализует паттерн синглтона для выполнения пайплайна: одновременно разрешена только одна активная инстанция пайплайна для каждого проекта.

### Семантика Синглтона
При попытке запустить второй пайплайн, когда первый уже работает, система вернёт ошибку `PIPELINE_ALREADY_RUNNING`.

### Структура `.workflow/logs/.pipeline.lock`

Файл пишется одной записью в момент захвата блокировки (`wx`), поэтому
плейсхолдеров `null` в нём не бывает. Между созданием файла и записью содержимого
есть микросекундное окно, в котором читатель может увидеть его пустым: пустой или
невалидный JSON следует трактовать как «повторить чтение», а не как «пайплайна нет».
Поля:

- `pid` — ID процесса работающего пайплайна
- `started_at` — временная метка запуска (ISO)
- `timestamp` — то же значение; оставлено для потребителей, читавших ранний формат
- `started_by` — кто запустил: `cli`, `mcp` или `extension`
- `started_by_id` — метка запустившего экземпляра; поля нет, если запускающий не представился
- `run_id` — идентификатор запуска, совпадает с именем лог-файла без расширения
- `pipeline_log` — путь к логу через `/`; относительный от корня проекта, а если `execution.log_file` указывает на другой диск — абсолютный
- `project_root` — корневая директория проекта
- `pipeline_version` — версия workflow-ai, записавшего блокировку

Поле `started_by` заполняется из переменной окружения `WORKFLOW_STARTED_BY`,
которую выставляет тот, кто спавнит раннер (workflow-mcp — `mcp`, расширение
VS Code — `extension`). По умолчанию `cli`; неизвестное значение отбрасывается.
Переменная снимается из окружения сразу после чтения, поэтому дочерние агенты
её не наследуют.

Поле `started_by_id` заполняется из `WORKFLOW_STARTED_BY_ID` — той же стороной
и по тем же правилам: переменная снимается сразу после чтения, значение длиннее
128 символов или с пробелами отбрасывается. Раннер его не расшифровывает, для
него это непрозрачная метка. Нужна она тому, кто запускал: workflow-mcp по ней
узнаёт собственный запуск и отличает его от запуска соседней рабочей области.
До 1.7.0 сервер писал для этого свой файл рядом (`.workflow/logs/.mcp-started-by`),
и два файла про один запуск умели разойтись.

Полный payload появился в 1.6.0; более ранние версии писали только
`pid`, `timestamp` и — с 1.5.2 — `started_at`. Наличие `started_by` служит
признаком раннера ≥ 1.6.0, наличие `started_by_id` — ≥ 1.7.0.

### Команды
- `workflow run --project <path> [--plan PLAN-X] [--config <path>]` — запустить пайплайн
- Остановка: программно через `stopPipeline()` из `src/lib/stop-command.mjs`
  либо через MCP-инструмент `stop_pipeline`. Команды `workflow stop` в CLI пока нет.

### Восстановление
Блокировка от упавшего процесса (kill -9, ребут, принудительное завершение на
Windows) остаётся на диске, но помечена мёртвым `pid`. Специальных действий не
нужно: следующий `workflow run` проверяет живость процесса, пишет
`stale marker found — removing` и снимает блокировку сам. Проверить вручную:
`node -e "console.log(require('fs').readFileSync('.workflow/logs/.pipeline.lock','utf8'))"`.

## Окружение агентов: `~/.workflow/agent.env`

Переменные из `<WORKFLOW_HOME>/agent.env` (по умолчанию `~/.workflow/agent.env`)
получает каждый агент — и в стадиях pipeline, и в тестах скилов, кто бы ни запустил
раннер (MCP, расширение VS Code, терминал). Типичное содержимое — прокси:

```
# строки KEY=VALUE; комментарий — только целая строка с '#' в начале
HTTP_PROXY=http://user:pass@host:port
HTTPS_PROXY=http://user:pass@host:port
ALL_PROXY=
```

`#` внутри значения — часть значения (не комментарий). Пустое значение
(`ALL_PROXY=`) убирает переменную из окружения агента. Файл перекрывает
окружение раннера, служебные `WORKFLOW_RAILS_*` главнее файла. Файл машинный и
вне git (в нём бывают учётные данные): в лог стадии пишутся только имена
переменных (`agent.env: задано HTTP_PROXY, HTTPS_PROXY; снято ALL_PROXY`),
значения — никогда; нечитаемый файл и строки не по формату — `WARN` с путём и
номерами строк. Читается при каждом запуске агента, перезапуск раннера после
правки не нужен. Нет файла — окружение агентов не меняется.

Зачем: 2026-09-24 автообновление kilo перезаписало обёртку `kilo.cmd`, которая
подставляла прокси; раннер из расширения запускал kilo напрямую, и все kilo-агенты
получили `403 Forbidden`. Реализация — `src/lib/agent-env.mjs`.

## Скилы для kilo

kilo CLI 7.7.x читает `SKILL.md` из проектного `.kilocode/skills`, только если
настоящий путь файла (после раскрытия всех ссылок) лежит внутри проекта; иначе —
`failed to load skill … blocked file reference outside project config scope`, и
агент работает без текста скила. Поэтому `workflow init` / `update` / `eject`:

- ставят ссылку `<каталог настроек kilo>/skills` → `~/.workflow/skills` — канон
  для всех проектов (каталог настроек: `KILO_CONFIG_DIR`, иначе
  `<XDG_CONFIG_HOME или ~/.config>/kilo`); своему каталогу kilo доверяет без
  проверки. Существующий каталог или чужую ссылку там не трогают;
- держат `.kilocode/skills` проекта обычным каталогом со ссылками только на скилы,
  физически лежащие в проекте (эжектнутые и проектные). Прежняя ссылка на весь
  `.workflow/src/skills` снимается — удаляется только ссылка, не цель.

Проверка: `kilo run "List the names of all skills available to you"` из корня
проекта — без строк `failed to load skill`.

## Фактическая модель kilo-агента

Роутеры kilo выбирают модель сами: `kilo/kilo-auto/free` — одну на сессию (от
сессии к сессии разную), `kilo/openrouter/free` — заново почти на каждом шаге.
Пока kilo-агент работает, раннер раз в 15 с смотрит, какие модели ответили, и при
смене набора пишет строку; после выхода агента — финальную, с числом шагов:

```
[execute-task] AGENT_MODELS agent="openrouter-free(nemotron, ling)" requested="kilo/openrouter/free" models="nvidia/nemotron-3-ultra-550b-a55b:free ×10, inclusionai/ling-3.0-flash-fin:free ×9"
```

`agent` — подпись агента: модель одна и совпадает с запрошенной — просто id
(`gpt-luna`); одна другая — в скобках её имя (`kilo-free(dots-3-note-preview)`);
несколько — семейства по убыванию шагов (`openrouter-free(nemotron, ling)`, семейство —
имя модели до первого дефиса). Та же подпись встаёт в столбец «Агент» истории работы
тикета и показывается в панели pipeline расширения VS Code. Метрики группируются по
id агента из конфига.

Источник — база kilo: kilo 7.7.9 записывает ответившую модель в каждый завершённый
шаг. Сессию запуска раннер находит по метке `kilo run --title workflow-<run id>`
(свой `--title` в аргументах агента не перекрывается), шаги субагентов считаются
вместе с ней. Путь базы спрашивается у `kilo db path` один раз на процесс раннера,
чтение — встроенным `node:sqlite` (Node ≥ 22.5). Нет модуля, базы или сессии — в
логе строка «фактическая модель неизвестна», на ход стадии это не влияет.
Реализация — `src/lib/kilo-models.mjs`.

## Runner-стадии

В системе поддерживаются различные типы стадий для управления процессами разработки:

### Human Gate

`human-gate` — стадия ручного контроля, которая требует вмешательства человека для продолжения выполнения пайплайна. Используется для критических точек, где необходима ручная проверка или утверждение.

**Условия срабатывания:**
- Стадия `manual-gate-human` блокирует пайплайн до ручного снятия gate
- Gate снимается через команду `move-ticket.js <id> unblock`
- Поддерживает настройку таймаутов и условий повторных попыток

**Пример конфигурации pipeline.yaml:**
```yaml
stages:
  - name: manual-gate-human
    type: manual-gate-human
    config:
      timeout: 3600  # 1 hour
      max_attempts: 3
      message: "Requires human approval before deployment"
```

Пример полного файла `pipeline.yaml` доступен в `docs/samples/pipeline-with-human-gate.yaml`.

### Autoblock notifications

Для автоматического блокировки тикетов при возникновении проблем используется механизм `mark-blocked`. Блокированные тикеты получают дополнительные поля в frontmatter для отслеживания причин и попыток:

- `auto_blocked_reason` — причина автоматической блокировки
- `auto_blocked_attempts` — количество попыток разблокировки
- `auto_blocked_at` — время автоматической блокировки

## Безынструментные агенты

Безынструментный агент — модель без инструментов и без доступа к файлам проекта:
вход для неё собирают и результат записывают скрипты стадии. Записи такого агента
бывают двух видов:

- `kind: http` — модель вызывает сам раннер по HTTP;
- агент с командой и маркером `tool_less: true` — обёртка, которая передаёт модели
  промпт и печатает её ответ, инструментов модели не даёт и в проекте читает только
  изображения, названные в промпте: `src/scripts/decisions-judge.js` (промпт из
  stdin, ключ из файла) или `src/scripts/claude-judge.js` (Claude без инструментов,
  изображения из промпта — раздел «Claude без инструментов — claude-judge.js»).

Такая модель подключается правкой `configs/pipeline.yaml`, без правок кода.

### Запись агента

```yaml
pipeline:
  agents:
    vision-chat:
      kind: http
      protocol: chat
      url: "https://openrouter.ai/api/v1/chat/completions"
      model: "<id мультимодальной модели>"
      auth: { file: "~/.workflow/secrets/openrouter.key" }
      timeout_s: 120
      capabilities: [text, multimodal]
    decisions-cli:
      command: "node"
      args: [".workflow/src/scripts/decisions-judge.js", "--model", "<id модели решений>",
             "--url", "https://openrouter.ai/api/alpha/decisions",
             "--key-file", "~/.workflow/secrets/openrouter.key"]
      prompt_stdin: true
      tool_less: true
      capabilities: [text]
```

| Поле | Значения | Обязательно |
|------|----------|-------------|
| `kind` | `cli` (по умолчанию) — агент с `command`; `http` — модель по HTTP, без `command` | нет |
| `protocol` | `chat` \| `decisions` | при `kind: http` |
| `url` | адрес `https://`; `http://` — только localhost, 127.0.0.1, ::1 (ключ уходит в заголовке) | при `kind: http` |
| `model` | id модели у провайдера | при `kind: http` |
| `auth` | `{ env: <ИМЯ> }` \| `{ file: <путь> }` \| `{ kilo_oauth: true }` — ровно одна форма | при `kind: http` |
| `timeout_s` | число > 0, по умолчанию 120; ограничивает одну попытку — с повторами вызов длится до 3 × `timeout_s` + 6 с | нет |
| `tool_less` | `true` — агент с командой не даёт модели инструментов и в проекте не читает ничего, кроме изображений, названных в промпте; заявление автора записи: раннер поле не читает и не проверяет | нет |
| `capabilities` | как у остальных агентов; `multimodal` — модель принимает изображения | как сейчас |

`command` и `args` у `kind: http` не задаются. Запись проверяется при старте
пайплайна; ошибка останавливает запуск с кодом 1 и называет агента и поле.

### Протоколы

- `chat` — формат OpenAI chat completions: системное сообщение и сообщение
  пользователя, поле `tools` не отправляется. Ответ — текст
  `choices[0].message.content` и источники из `annotations` (`url_citation`).
  Изображения — частями `image_url` с data URL: PNG, JPEG или WebP, до 5 МБ на
  файл, до 8 на запрос. Приём `image_url` конкретной моделью OpenRouter не проверен.
- `decisions` — типизированная оценка OpenRouter: тело `{ model, state, questions }`,
  ответ — вероятности уровней и уверенность по каждому вопросу. Изображений не принимает.

Общее: ключ `Authorization: Bearer`; прокси из `HTTPS_PROXY` / `HTTP_PROXY` /
`ALL_PROXY` (туннель CONNECT, только для `https://`); до двух повторов с паузами
2 и 4 с при HTTP 429, 500, 502, 503 и сетевой ошибке. Ошибка получает класс:

| Класс | Когда |
|-------|-------|
| `no_key` | переменная из `auth.env` пуста; файла ключа (`auth.file`) нет или он пуст; файла kilo нет; токен kilo истёк |
| `auth` | HTTP 401, 403 |
| `rate_limit` | HTTP 429 после повторов |
| `server` | HTTP 5xx после повторов |
| `timeout` | истёк `timeout_s` |
| `network` | соединение с сервером или прокси не установлено после повторов |
| `bad_request` | прочие HTTP 4xx; изображения для `decisions`; вложение сверх ограничений; `http://` не на свою машину |
| `bad_response` | ответ не JSON; нет полей протокола; нет ответа на вопрос; уровень вне 1..n |
| `aborted` | запрос снят остановкой пайплайна (SIGINT/SIGTERM) |

Реализация — `src/lib/model-client.mjs`.

### Авторизация

- `{ env: <ИМЯ> }` — ключ только из переменной окружения раннера или машинного
  `~/.workflow/agent.env`. В репозиторий и в `pipeline.yaml` ключ не пишется.
  Переменную окружения наследуют все процессы раннера, в том числе агенты стадий.
- `{ file: <путь> }` — ключ из файла (одна строка; `~` — домашний каталог), как у
  claude и kilo: в окружении процессов его нет. Нет файла или он пуст — `no_key`.
- `{ kilo_oauth: true }` — токен `kilo.access` из `~/.local/share/kilo/auth.json`;
  истёкший токен — ошибка `no_key` с подсказкой `kilo auth login`.

Ключ не попадает ни в лог, ни в сообщения ошибок. На Windows имя переменной
(ключа и прокси) ищется без учёта регистра, как его видят CLI-агенты:
`Model_Api_Key` в системе находится по `auth: { env: MODEL_API_KEY }`.

### Слой оценки

Один вход и выход для обоих протоколов (`src/lib/model-evaluate.mjs`): скриптам
стадии не нужно знать протокол выбранной модели.

```json
{
  "data": "<строка или объект — что оценивается>",
  "images": ["<путь к изображению>"],
  "questions": [{ "id": "dod-3", "text": "<вопрос>", "levels": ["<уровень 1>", "…", "<уровень n>"] }]
}
```

Выход — `{ answers: { <id>: { level, confidence, probabilities, reason } }, model,
usage, cost_usd, duration_ms }`, `level` — номер уровня 1..n, уровней от 2 до 10.
У `decisions` уровень — наибольшая вероятность (при равенстве — меньший уровень),
`confidence` — из ответа. У `chat` модель отвечает JSON
`{"answers":[{"id","level","reason"}]}`, `confidence` — `null`; из текста берётся
первый JSON-объект с массивом `answers`, уровень — целое число или строка из цифр.
Нет ответа на вопрос или уровень вне диапазона — `bad_response`, уровня по умолчанию нет.
Порог прохода решает потребитель.

### Стадия с обменом model_io

```yaml
    review:
      agents: [decisions-cli, vision-chat]
      model_io:
        prepare: "<путь к node-скрипту от корня проекта>"
        apply: "<путь к node-скрипту от корня проекта>"
        options: { }          # необязательно; передаётся обоим скриптам
```

Какого бы агента ни выбрал `resolveAgent` — `kind: http` или с командой, — стадия
с `model_io` идёт в три шага. Скил стадии агент не исполняет:

1. **prepare** — `node <prepare> "<промпт стадии>"`. Переменные: `WORKFLOW_MODEL_AGENT`,
   `WORKFLOW_MODEL_CAPABILITIES` (JSON), `WORKFLOW_MODEL_IO_OPTIONS` (JSON `options`).
   Результат `status: ready` с `request_file: <путь к входу слоя оценки>` ведёт
   к шагу 2. Любой другой результат — результат стадии: так prepare сам закрывает
   стадию, когда спрашивать нечего. `ready` без `request_file` или нечитаемый JSON —
   `status: error` с `error_class: bad_prepare`: ошибка скрипта отличима от отказа модели.
2. **Модель** — по виду агента:
   - `kind: http` — раннер зовёт слой оценки, все вопросы одним запросом;
   - агент с командой — на каждый вопрос отдельный запуск с промптом судьи тестов
     скилов (раздел «Судья тестов скилов»): в `## Rubric` — строки `| n | <уровень> |`
     из `levels` вопроса, в `## Target Agent Output` — `data` (объект — JSON), а при
     непустом `images` ещё строка `Изображения:` и пути по одному в строке, в `## Task` —
     текст вопроса. Ответ — блок `---RESULT---` со `score` 1..5 и необязательными
     `reason`, `confidence`, `probabilities`, `model`, `cost_usd`; раннер собирает ответы в
     выход той же формы, что у слоя оценки (`usage: null`; `cost_usd` — сумма по
     вопросам или `null`, если хоть один ответ цены не назвал). Вопрос не ровно с
     пятью уровнями — `bad_request` до запуска агента; ответ без балла — `unparsed`;
     ответ с `error_class` — ошибка этого класса. Переоценки по `escalate_to` нет.
     В лог вместо текста промпта — строка `question=<id> prompt_chars=<длина>`.

   Ответ раннер пишет в `.workflow/state/model-io/<стадия>-<run_id пайплайна>-<id вызова>.json`.
   Ошибка — результат стадии `status: error` с `error_class`, шаг 3 не выполняется.
3. **apply** — `node <apply> "<промпт стадии>"` с теми же переменными плюс
   `WORKFLOW_MODEL_REQUEST` и `WORKFLOW_MODEL_RESPONSE` (пути файлов). Его
   `---RESULT---` — результат стадии.

Таймаут prepare и apply — `execution.timeout_per_stage`, одной попытки вызова
модели — `timeout_s` агента `kind: http`, одного запуска агента с командой —
`execution.timeout_per_stage`. Остановка пайплайна снимает запрос к модели сразу и
не запускает apply: результат — `status: error`, `error_class: aborted`. В лог пишется строка
`MODEL_IO agent="…" model="…" status=… prepare_ms=… model_ms=… apply_ms=… cost_usd=…`.

Ошибки `auth`, `rate_limit`, `server`, `timeout`, `network` — у агента с командой это
`error_class` его ответа — помечают агента в health-реестре, как падение CLI-агента,
и стадия переходит к следующему агенту списка. Остальные классы (`no_key`,
`bad_request`, `bad_response`, `bad_prepare`, `aborted`, `unparsed` и прочие классы
из ответа агента с командой) агента не помечают: стадия
уходит по `goto.error`, а следующая попытка стадии (по её счётчику) берёт
следующего агента. В истории работы тикета такой запуск записывается как `error`.
Сбой процесса prepare, apply или агента с командой (выход ≠ 0 без `---RESULT---`,
таймаут) обрабатывается как падение CLI-агента.

**Выбор модели.** Стадия перечисляет агентов по приоритету, контекст несёт
`required_capabilities`. Остаются агенты, у которых есть все требуемые способности:
нужны изображения (`["multimodal"]`) — только мультимодальные. Попытка N берёт N-го
из оставшихся по кругу, первая — первого по приоритету.

Проверка конфига требует файлы `prepare` и `apply` на диске от корня проекта; путь
`.workflow/src/…`, которого нет, ищется ещё и по `src/…` — так конфиг проходит
проверку в репозитории workflow-ai, где `.workflow/` нет (CI) или он ведёт на
установленную версию. Запуск берёт путь как записан.

### Защита от ошибочного назначения

Проверка конфига при старте пайплайна (`validateConfig`) отклоняет:

- агента `kind: http` в `stage.agent`, `stage.agents` или
  `stage.agents_by_type.<тип>.agents` стадии без `model_io`;
- агента `kind: http` в `pipeline.default_agents` и `pipeline.default_agent` — всегда.

Тесты скилов (`run-skill-tests.js`) не берут агента `kind: http` исполнителем:
`target_agents` скила или кейса и `--agent` с таким агентом завершают прогон
ошибкой до первого вызова модели. Судьёй (`judge_agent`) — тоже: судья — агент с
командой (раздел «Судья тестов скилов»).

Способности от ошибочного назначения не защищают: фильтр `resolveAgent`
пропускает агента, у которого есть все требуемые способности, а `[text]` есть почти
у всех. Поэтому защита строится на виде записи.

Агента с командой в стадии с `model_io` проверка не отклоняет: он отвечает на
вопросы по контракту судьи, а не исполняет скил. Агент с инструментами и доступом
к репозиторию (`claude` с `--permission-mode bypassPermissions`, `kilo run --auto`)
в такой стадии может прочитать файлы проекта сам. Безынструментность агента с
командой — маркер `tool_less: true`, заявление автора записи; раннер его не проверяет.

### Как добавить модель

1. Добавить в `pipeline.agents` запись `kind: http` или агента с командой без
   инструментов у модели, с `tool_less: true` (примеры выше).
2. Ключ — в файле: `auth: { file: <путь> }` у `kind: http`, аргумент обёртки у агента
   с командой (`--key-file` у `decisions-judge.js`).
3. Вписать агента в список `agents` стадии с `model_io` — по приоритету.
4. Для модели с изображениями — добавить `multimodal` в `capabilities`. Агент с
   командой получает изображения путями в строках после `Изображения:` и сам
   передаёт их модели (так делает `claude-judge.js`).

## Судья тестов скилов

L2-оценку в тестах скилов (`src/scripts/run-skill-tests.js`) даёт судья — агент
с командой из `pipeline.agents`, названный в `execution.judge_agent` файла
`tests/index.yaml` скила. Файлы скилов правятся через коуча. У системы нет
отдельной ветки ни для конкретной модели, ни для её протокола или ключа: судья
получает текстовый промпт и отвечает текстом.

### Промпт и ответ судьи

Промпт — рубрика, вывод исполнителя с файлами тикета и критерий кейса (секции
`## Rubric`, `## Target Agent Output`, `## Task`). Ответ — блок `---RESULT---`:

| Поле | Обязательно | Что |
|------|-------------|-----|
| `score` | да | балл 1..5; попытка проходит при 4 и выше |
| `confidence` | нет | уверенность 0..1 — по ней работает переоценка |
| `cost_usd` | нет | цена ответа |
| `model`, `probabilities` | нет | модель из ответа и вероятности уровней (JSON) |
| `status: error`, `error_class`, `error` | при сбое | ответ без балла: класс и текст сбоя |

Ответ без балла и балл вне 1..5 — ошибка попытки, а не балл по умолчанию.
`prompt_stdin: true` в записи агента — промпт через stdin, а не последним
аргументом: на Windows аргумент ограничен 32767 символами.

### Модель с другим протоколом — CLI-обёртка

Модель решений (OpenRouter `decisions`: вероятности уровней вместо текста)
подключается обёрткой `src/scripts/decisions-judge.js`. Она берёт уровни из
таблицы рубрики (`| n | текст |`, `src/lib/rubric-levels.mjs`), спрашивает модель
и печатает `score` (самый вероятный уровень, при равенстве — меньший) и
`confidence`. Модель, адрес и файл ключа — аргументы агента:

```yaml
    jev:
      command: "node"
      args: [".workflow/src/scripts/decisions-judge.js", "--model", "typesafe/jev-1.13",
             "--url", "https://openrouter.ai/api/alpha/decisions",
             "--key-file", "~/.workflow/secrets/openrouter.key"]
      prompt_stdin: true
      escalate_to: claude-opus   # переоценка и фоллбек
      escalate_below: 0.8        # уверенность ниже — переоценка
      escalation_share: 0.292    # доля переоценки — для оценки цены
      cost_per_call: 0.0001
```

Ключ обёртка читает сама из файла `--key-file` (одна строка, `~` — домашний
каталог), как claude и kilo: в переменных окружения, которые наследуют все
процессы, его нет. Нет файла — ответ `error_class: no_key`. Адрес прокси или
сервера в тексте сетевой ошибки заменяется на `[address]` / `[host:port]`.
**Выводы исполнителей и содержимое тестовых тикетов уходят в OpenRouter и
TypeSafe** (согласие стейкхолдера — 2026-09-26).

### Переоценка и фоллбек

Поля записи агента-судьи:

- `escalate_to` — агент с командой, который переоценивает; без него переоценки нет;
- `escalate_below` — уверенность ниже порога или её отсутствие в ответе — попытку
  переоценивает `escalate_to`, итог — его балл;
- ответ без балла (сбой судьи) — тоже `escalate_to`, с пометкой `fallback: <класс>`;
  предупреждение — одно на класс сбоя за прогон. Прогон не падает.

Судья по умолчанию во всех скилах — `jev` с переоценкой `claude-opus` (с
2026-09-26, по перемеру согласия: pass/fail 94.7%, при пороге 0.8 на оставшихся
оценках 100%). Таймаут судьи — `execution.judge_timeout_s` скила (по умолчанию
180 с); у обёртки свой `--timeout` на запрос к модели.

### Запись вызова судьи

По каждой попытке раннер пишет `current/<agent>/trial-<N>.judge.json` рядом с
`trial-<N>.md`, и при ошибке судьи тоже. Записи попыток, которых в прогоне нет,
снимаются. Поля:

| Поле | Что |
|------|-----|
| `judge_agent` | судья |
| `input` | `rubric_file`, `rubric`, `criterion`, `agent_output`, `ticket_files` |
| `prompt`, `raw_output` | промпт и ответ судьи как есть |
| `own_score` | балл этого судьи |
| `score`, `passed` | итог попытки (после переоценки или фоллбека) |
| `confidence`, `probabilities`, `model`, `cost_usd` | поля ответа судьи |
| `escalated`, `escalation` | переоценка по уверенности и запись вызова `escalate_to` |
| `fallback`, `fallback_detail` | класс и текст сбоя, из-за которого оценку дал `escalate_to` |
| `duration_ms` | длительность |
| `error`, `error_class` | ошибка судьи — попытка `errored` |

### Цена в оценке перед прогоном

Цена вызова судьи — `cost_per_call` его записи; с `escalate_to` к ней добавляется
`escalation_share` × цена `escalate_to`. Без `cost_per_call` — $0.02, без
`escalation_share` — переоценка каждой оценки; о недостающем поле — предупреждение.
Рядом печатается худший случай — судья не дал балла ни разу (нет ключа, сбой), и
каждую оценку дал ещё и `escalate_to`.

### Перемер согласия судей

```bash
# записи прогона с судьёй, у которого есть переоценка: оценки судьи переоценивает его escalate_to
node src/scripts/compare-judges.js --judge claude-opus \
  --out .workflow/reports/judge-agreement-<дата>.md \
  --disagreements .workflow/reports/judge-agreement-<дата>/

# записи прогона с судьёй без переоценки: их переоценивает судья с уверенностью
node src/scripts/compare-judges.js --judge jev --out … --disagreements …
```

Скрипт переоценивает сохранённые записи судьёй `--judge` без запуска исполнителей
и сравнивает с баллом записи. Судья оценивает сам, без переоценки. Отчёт даёт:

- совпадение точное, ±1 и pass/fail;
- матрицу 5×5 и разбивку по скилам;
- таблицу порогов уверенности 0.7 / 0.8 / 0.95: доля переоценки, совпадение на
  оставшихся, сколько расхождений проходит мимо порога — только когда `--judge`
  сообщает уверенность;
- цену.

Каждое расхождение pass/fail — отдельный файл с входом и обоими ответами. Записи с
ошибкой судьи пропускаются и считаются отдельно. У записи, балл которой дал
`escalate_to` (переоценка или фоллбек), судьёй записи считается он. Запись, балл
которой дал сам `--judge`, пропускается: судья совпал бы сам с собой. `--skill <имя>`
сужает выборку. Перед вызовами — число вызовов, цена и вопрос; `--yes` вопрос
пропускает. Записи есть, а не сравнена ни одна (нет ключа, все с ошибкой или с
баллом самого `--judge`) — код выхода 1.

Когда записи сделаны судьёй с переоценкой, согласие перемеряет его `escalate_to`:
он переоценивает оценки судьи, не ушедшие на переоценку, — именно те, что попадают
в итог без проверки. Порог уверенности так не перемерить: оценки ниже порога уже
ушли на переоценку. Для таблицы порогов нужен прогон с судьёй без переоценки и
`--judge` с уверенностью.

Реестр агентов оба скрипта берут из `.workflow/config/pipeline.yaml` проекта, а это
копия конфига установленной версии workflow-ai; другой конфиг — `--pipeline <путь>`.
Скрипт-обёртка в записи агента (`.workflow/src/scripts/decisions-judge.js`) — тоже
из установленной версии: пока её нет в `.workflow/src/scripts`, судья отвечает
сбоем, и каждую оценку даёт `escalate_to`.

## Формат DoD 2 и ревью по evidence

Тикет с `dod_format: 2` во frontmatter несёт под каждым пунктом «Критериев
готовности» машиночитаемую проверку. Детерминированные пункты закрывает скрипт,
прозаические и пункты со скриншотами оценивает модель стадии ревью — по evidence,
которые собрали скрипты, а не по разделу Result исполнителя. Разбор записи и
исполнитель проверок — `src/lib/check-runner.mjs`.

### Формы проверки

Проверка — вложенный пункт с отступом под пунктом DoD `- [ ] …`: ключи латиницей,
значения в обратных кавычках, пары через запятую. У пункта ровно одна форма; прочие
вложенные строки, которые не начинаются с ключа проверки, не учитываются.

```markdown
## Критерии готовности (Definition of Done)

- [ ] Раннер сохраняет запись вызова судьи по каждой попытке
  - check: `node -e "process.exit(require('fs').existsSync('out/judge.json') ? 0 : 1)"`, expect: `exit 0`
- [ ] Прежние тесты раннера зелёные
  - check: `npm test`, expect: `exit 0`, regression: `true`
- [ ] Текст ошибки понятен пользователю
  - prose: `понятность формулировки командой не проверить`
- [ ] Кнопка «Экспорт» стоит справа от поиска
  - visual: `.workflow/evidence/screens/IMPL-041-*.png`
```

| Форма | Значение | Кто оценивает |
|-------|----------|---------------|
| `check` + `expect` | одна команда (ограничения — ниже) и ожидание | скрипт, без модели |
| `check` + `expect` + `regression` | значение `` `true` `` — в обратных кавычках, иначе запись не разобрана; проверка зелёная и до работы: прогон существующего теста или `npm test` | скрипт, без модели |
| `prose` | непустая причина, почему командой не проверить | модель стадии ревью |
| `visual` | путь или маска изображений от корня проекта; `*` и `?` действуют внутри одного сегмента пути; в список идут только PNG, JPEG, WebP внутри корня; файлы кладёт исполнитель тикета | агент стадии ревью со способностью `multimodal` |

| `expect` | Проходит, когда |
|----------|-----------------|
| `exit <N>` | код возврата равен N |
| `stdout contains <текст>` | stdout содержит текст |
| `stdout not contains <текст>` | stdout не содержит текст |
| `stdout matches /<регэксп>/` | регэксп JavaScript (без флагов) находит совпадение в stdout |

Для видов stdout код возврата не сравнивается. Ожидание другого вида или
неразбираемый регэксп — отказ `denied`, команда не запускается.

В плане проверки записываются у критерия приёмки задачи после `**Проверка:**` — одна
в той же строке или несколько вложенным списком (`templates/plan-template.md`); при
декомпозиции каждая запись становится проверкой одного пункта DoD.

### Ограничения исполнителя проверок

| Правило | Значение |
|---------|----------|
| Исполняемые файлы | `node`, `npm` (только `test` и `run <скрипт>`), `git` (только `status`, `diff`, `log`, `show`, `ls-files`, `rev-parse`, `grep`), `pytest`, `python`, `dotnet`, `rg`, `grep` |
| Опции | `npm` — после подкоманды только `--` и аргументы скрипту (собственные опции npm, например `--script-shell`, запрещены); `git` — подкоманда первым аргументом (глобальные `-c`, `-C` не проходят), `-O` / `--open-files-in-pager` запрещены; `rg` — `--pre` и `--hostname-bin` запрещены: они запускают другую программу |
| Операторы оболочки | вне кавычек `;`, `&`, `&&`, `\|`, `\|\|`, `<`, `>`, `` ` ``, `$(` — отказ; внутри двойных кавычек — только `` ` `` и `$(`; внутри одинарных всё буквально |
| Запуск | без оболочки: команда разбирается в argv по правилам POSIX-оболочки без подстановок, обратная косая вне кавычек — обычный символ (пути Windows); `npm` на Windows запускается как `node …/npm-cli.js` рядом с `npm.cmd` |
| Рабочий каталог | корень проекта |
| Таймаут | 120 с на проверку; по истечении снимается всё дерево процессов, статус `timeout` |
| Вывод | stdout и stderr — последние 4000 символов каждого, с пометкой об усечении; ожидание сверяется с полным выводом; в памяти — до 16 МБ каждого потока, stdout больше — ожидание вида stdout даёт `failed` с причиной `stdout_too_large` |

Нарушение — статус `denied`, процесс не запускается. Хуки Claude Code этих команд не
видят — их запускает скрипт пайплайна, поэтому защита только в исполнителе. `node`,
`python` и `npm run` исполняют код репозитория; сетевой изоляции у запущенного
процесса нет.

### Проверки до работы

- `verify-atomicity.js` при декомпозиции даёт FAIL тикету `dod_format: 2`, у которого
  нет пунктов DoD, есть пункт без ровно одной полной формы или все пункты —
  регрессионные проверки: такой тикет ничего не утверждает о результате работы.
- `move-to-ready.js` перед переносом тикета `dod_format: 2` в `ready/` исполняет его
  проверки `check` без пометки `regression` — до работы они обязаны быть красными.
  Зелёная, отклонённая (`denied`), упавшая по таймауту или неразобранная проверка
  отправляет тикет в `blocked/` с причиной в `blocked_reason`. Тикет `type: human`
  переносится без гейта.

### Evidence и исходы предпроверки

Стадия `verify-artifacts` по тикету `dod_format: 2` пишет файл
`.workflow/state/evidence/<имя файла тикета>.json`, каждая попытка — заново:

- `items` — пункты DoD: проверки `check` с командой, кодом возврата, выводом и
  статусом (`passed`, `failed`, `timeout`, `denied`); `prose` и `visual` с
  изображениями — `pending`; `visual` без файлов — `image_missing`; неразобранная
  запись — `failed` с причиной `dod_record_invalid`;
- `source_refs` — ссылки `file:line` из раздела Result, сверенные с диском: найденная —
  строки исходника ±5 с номерами, иначе `status: missing`. Сам текст Result в
  evidence не попадает;
- `diff` — по «Изменённым файлам»: изменения относительно `HEAD` и новые файлы целиком,
  без каталога тикетов; до 60 000 символов, сверх — начало и `diff_truncated`;
  несобранная часть — причина в `diff_error`;
- `legacy_gates` — прежние гейты; `review` — заполняет стадия ревью.

| Исход | Когда | Куда |
|-------|-------|------|
| `all_green` | все пункты — зелёные `check`, прежние гейты пройдены | `move-ticket` в `done` без модели; в `## Ревью` — строка `passed` с путём evidence |
| `passed` | проверки зелёные, есть пункты `prose` или `visual` | `review-result` с `evidence_file` и `required_capabilities` |
| `legacy` | тикет без `dod_format: 2`, прежние гейты пройдены | `review-result-legacy` |
| `failed` | провален прежний гейт (Result пуст, ни один пункт DoD не отмечен, файлы отсутствуют или не менялись, source-grounding, implementation assertions) или пункт DoD; у тикета `dod_format: 2` нет пунктов DoD | `increment-task-attempts`, без ревью; в `## Ревью` — строка `failed` с причинами (у тикета `dod_format: 2` — и с путём evidence) |

Исход `default` ведёт в `review-result`, `error` — в `review-result-legacy`
(`configs/pipeline.yaml`, стадия `verify-artifacts`).

### Стадия ревью

```yaml
    review-result:
      agents: [jev, claude-haiku-vision]
      counter: task_attempts
      model_io:
        prepare: ".workflow/src/skills/review-result/scripts/prepare-review.js"
        apply: ".workflow/src/skills/review-result/scripts/apply-review.js"
        options: { pass_level: 4, min_confidence: 0.8 }
```

Стадия идёт по обмену `model_io` (раздел «Стадия с обменом model_io»), одинаково для
любого агента списка:

1. `prepare-review.js` читает `evidence_file` из контекста и строит вопросы — по
   одному на пункт `prose` и `visual`: id `dod-<номер пункта>`, текст пункта (у
   `visual` — с путями изображений), пять уровней шкалы
   `src/skills/review-result/knowledge/dod-evidence-scale.md`. В `data` — пункты с
   результатом, `source_refs` и дифф; раздела Result тикета там нет. Вопросов нет —
   `status: passed` без модели. Отказы: `evidence_missing`, `evidence_invalid`,
   `evidence_mismatch` (evidence другого тикета), `evidence_failed_items`,
   `agent_without_multimodal` (есть изображения, а у агента нет `multimodal`).
2. Модель отвечает уровнем на каждый вопрос: агент с командой — отдельным запуском
   на вопрос, агент `kind: http` — одним запросом.
3. `apply-review.js` засчитывает пункт при уровне не ниже `pass_level` и уверенности
   не ниже `min_confidence` или без уверенности (агент её не сообщает). Неуверенная
   оценка — провал, переоценки нет. Уровни, уверенность, агент и модель пишутся в
   раздел `review` файла evidence и строкой в `## Ревью`; результат `passed` ведёт в
   `move-ticket` `done`, `failed` и `error` — в `increment-task-attempts`, то есть в
   `ready/` на повторное исполнение тикета, а когда счётчик `task_attempts` доходит
   до `max: 6` (`max_reached`) — в `mark-blocked` и `blocked/`; `default` — в
   `move-ticket` `backlog`. Следующее ревью по счётчику `task_attempts` берёт
   следующего подходящего агента списка по кругу.

**Выбор агента.** `verify-artifacts` отдаёт `required_capabilities` — способности
тикета плюс `multimodal`, если есть пункт `visual`. Есть скриншоты — остаются только
агенты с `multimodal`; нет — все агенты списка, у которых есть способности тикета.
Первая попытка берёт первого из оставшихся по приоритету, следующие — по кругу. В
действующем конфиге (`jev` — `[text]`, `claude-haiku-vision` — `[text, multimodal]`)
единственный агент с `multimodal` — `claude-haiku-vision`: скриншоты ревьюит он, а
тикет без них и без своего требования `multimodal` на первой попытке — `jev`.

**Почему в списке только `kind: http` и `tool_less: true`.** Модель должна видеть
только evidence. Агент с инструментами и доступом к репозиторию прочтёт тикет и его
Result сам, и тогда оценка опирается на заявления исполнителя. Раннер вид агентов
списка не проверяет — это правило состава конфига.

**Данные проектов — тексты пунктов DoD, вывод проверок, фрагменты исходников, дифф
и скриншоты — уходят провайдеру модели выбранного агента: в действующем конфиге
OpenRouter и TypeSafe (`jev`) или Anthropic (`claude-haiku-vision`)** (согласие
стейкхолдера — 2026-09-26).

### Claude без инструментов — claude-judge.js

`src/scripts/claude-judge.js` — агент с командой: передаёт промпт судьи модели Claude
без инструментов вместе с изображениями, которые в нём названы, и печатает ответ в
формате судьи:

```yaml
    claude-haiku-vision:
      command: "node"
      args: [".workflow/src/scripts/claude-judge.js", "--model", "claude-haiku-4-5-20251001"]
      workdir: "."
      prompt_stdin: true
      tool_less: true
      capabilities: [text, multimodal]
```

- Аргументы: `--model` (обязателен), `--command` (исполняемый файл claude, по
  умолчанию `claude`), `--arg` (аргумент перед своими, можно повторять), `--timeout`
  (секунды, по умолчанию 180). Промпт — из stdin или последним аргументом.
- Изображения — пути из строк после `Изображения:` в `## Target Agent Output`; они
  уходят модели блоками base64, а не путями. Только внутри рабочего каталога агента
  (корень проекта), PNG, JPEG или WebP, до 5 МБ на файл и до 8 на запрос.
- Каждый `@` текста заменяется на `＠` (U+FF20): Claude Code прикладывает к запросу
  файл, упомянутый как `@путь`, и строка `@файл` из диффа или пункта DoD отдала бы
  модели файл, которого нет в evidence.
- claude запускается с `--tools ""` и `--strict-mcp-config` — без инструментов и MCP,
  с `--setting-sources project` в пустом временном каталоге — без пользовательских
  настроек и хуков. Каталог снимается после ответа.
- Ответ — `---RESULT---` со `score`, `reason`, `model`, `cost_usd`, `images` (число
  приложенных изображений). Сбой — `status: error`, `error_class` (`usage`,
  `bad_prompt`, `bad_request`, `unparsed`, `timeout`, `agent_error`), `error` и код
  выхода 1.

### Таблица «## Ревью» — запись для человека

Строки в таблицу пишут стадии пайплайна, но строку `passed` может дописать и сам
исполнитель. Поэтому в `done/` тикет переносят только стадии пайплайна по своим
результатам; текст таблицы решает лишь откат из `done/` тикета без `completed_at`.

- `move-to-review` возвращает в `review/` любой тикет, найденный в `done/`, какая бы
  строка ни стояла в таблице.
- Авто-коррекция `pick-next-task` (`configs/ticket-movement-rules.yaml`) не переносит
  тикет в `done/` по строке `passed` или `skipped` ни из одной колонки. Осталось
  направление «из `done/`»: последняя строка `failed` или строки нет — тикет уходит в
  `backlog/`, кроме тикетов с заполненным `completed_at`.
- В `done/` пайплайн переносит тикет стадией `move-ticket` по результату своих
  стадий — например, `all_green` предпроверки или `passed` стадии ревью.

### Тикеты без dod_format: 2

Тикет без поля (в том числе все тикеты, созданные до формата) идёт прежним
маршрутом: `verify-artifacts` отвечает `legacy`, и ревьюит стадия
`review-result-legacy` — прежняя запись `review-result` под новым id: агенты
`[claude-haiku, gpt-luna, gemini-flash-lite, claude-sonnet]`, скил `review-result`,
счётчик `task_attempts`. Evidence для такого тикета не собирается, гейт
`move-to-ready` и проверка форм в `verify-atomicity.js` к нему не применяются. Туда
же ведёт исход `error` предпроверки.
