## Синглтон семантика Pipeline

Система workflow реализует паттерн синглтона для выполнения пайплайна: одновременно разрешена только одна активная инстанция пайплайна для каждого проекта.

### Семантика Синглтона
При попытке запустить второй пайплайн, когда первый уже работает, система вернёт ошибку `PIPELINE_ALREADY_RUNNING`.

### Структура `.workflow/logs/.pipeline.lock`

Файл пишется одной записью в момент захвата блокировки (`wx`), поэтому
плейсхолдеров `null` в нём не бывает. Между созданием файла и записью содержимого
есть микросекундное окно, в котором читатель может увидеть его пустым: пустой или
невалидный JSON следует трактовать как «повторить чтение», а не как «пайплайна нет».
Поля:

- `pid` — ID процесса работающего пайплайна
- `started_at` — временная метка запуска (ISO)
- `timestamp` — то же значение; оставлено для потребителей, читавших ранний формат
- `started_by` — кто запустил: `cli`, `mcp` или `extension`
- `started_by_id` — метка запустившего экземпляра; поля нет, если запускающий не представился
- `run_id` — идентификатор запуска, совпадает с именем лог-файла без расширения
- `pipeline_log` — путь к логу через `/`; относительный от корня проекта, а если `execution.log_file` указывает на другой диск — абсолютный
- `project_root` — корневая директория проекта
- `pipeline_version` — версия workflow-ai, записавшего блокировку

Поле `started_by` заполняется из переменной окружения `WORKFLOW_STARTED_BY`,
которую выставляет тот, кто спавнит раннер (workflow-mcp — `mcp`, расширение
VS Code — `extension`). По умолчанию `cli`; неизвестное значение отбрасывается.
Переменная снимается из окружения сразу после чтения, поэтому дочерние агенты
её не наследуют.

Поле `started_by_id` заполняется из `WORKFLOW_STARTED_BY_ID` — той же стороной
и по тем же правилам: переменная снимается сразу после чтения, значение длиннее
128 символов или с пробелами отбрасывается. Раннер его не расшифровывает, для
него это непрозрачная метка. Нужна она тому, кто запускал: workflow-mcp по ней
узнаёт собственный запуск и отличает его от запуска соседней рабочей области.
До 1.7.0 сервер писал для этого свой файл рядом (`.workflow/logs/.mcp-started-by`),
и два файла про один запуск умели разойтись.

Полный payload появился в 1.6.0; более ранние версии писали только
`pid`, `timestamp` и — с 1.5.2 — `started_at`. Наличие `started_by` служит
признаком раннера ≥ 1.6.0, наличие `started_by_id` — ≥ 1.7.0.

### Команды
- `workflow run --project <path> [--plan PLAN-X] [--config <path>]` — запустить пайплайн
- Остановка: программно через `stopPipeline()` из `src/lib/stop-command.mjs`
  либо через MCP-инструмент `stop_pipeline`. Команды `workflow stop` в CLI пока нет.

### Восстановление
Блокировка от упавшего процесса (kill -9, ребут, принудительное завершение на
Windows) остаётся на диске, но помечена мёртвым `pid`. Специальных действий не
нужно: следующий `workflow run` проверяет живость процесса, пишет
`stale marker found — removing` и снимает блокировку сам. Проверить вручную:
`node -e "console.log(require('fs').readFileSync('.workflow/logs/.pipeline.lock','utf8'))"`.

## Runner-стадии

В системе поддерживаются различные типы стадий для управления процессами разработки:

### Human Gate

`human-gate` — стадия ручного контроля, которая требует вмешательства человека для продолжения выполнения пайплайна. Используется для критических точек, где необходима ручная проверка или утверждение.

**Условия срабатывания:**
- Стадия `manual-gate-human` блокирует пайплайн до ручного снятия gate
- Gate снимается через команду `move-ticket.js <id> unblock`
- Поддерживает настройку таймаутов и условий повторных попыток

**Пример конфигурации pipeline.yaml:**
```yaml
stages:
  - name: manual-gate-human
    type: manual-gate-human
    config:
      timeout: 3600  # 1 hour
      max_attempts: 3
      message: "Requires human approval before deployment"
```

Пример полного файла `pipeline.yaml` доступен в `docs/samples/pipeline-with-human-gate.yaml`.

### Autoblock notifications

Для автоматического блокировки тикетов при возникновении проблем используется механизм `mark-blocked`. Блокированные тикеты получают дополнительные поля в frontmatter для отслеживания причин и попыток:

- `auto_blocked_reason` — причина автоматической блокировки
- `auto_blocked_attempts` — количество попыток разблокировки
- `auto_blocked_at` — время автоматической блокировки
